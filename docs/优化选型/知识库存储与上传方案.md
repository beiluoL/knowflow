### 1.3 具体缺陷清单

**P0 — 目录导入会整批失败**

```js
// KnowledgeImport.vue:548-553
const formData = new FormData()
for (const file of selectedFiles.value) {
  formData.append('files', file, relPath)   // 全部文件塞进同一个请求
}
```

- `spring.servlet.multipart.max-request-size: 500MB`（`application.yml:36`）→ 目录超 500MB 直接 **413，一篇都进不去**
- 无文件数上限、无单文件体积校验、无 `accept` 白名单（`:123-125`）
- 网络抖动 / 超时 → **已传的 99% 全部作废**，从零重来
- `timeout: 300000`（`api/knowledgeImport.ts:16`）→ 大目录必超时，因为后端 Tika 解析是**同步**的

**P0 — 进度条是假的**

```html
<!-- KnowledgeImport.vue:271 -->
<div class="progress-bar-fill" style="width: 100%"></div>
```

用户看到的是一条来回脉冲的动画条，与真实传输字节数**零关联**。10GB 目录和 10KB 文件的视觉表现完全一样。

**P1 — 分片能力完全缺失**

全仓搜索 `chunk|shard|md5|resume|part` 后确认：
- `doc_chunk` 表（`schema.sql:802`）是 **RAG 语义分块**，与上传分片无关
- 无 `/chunk`、`/merge`、`/check` 接口，无分片记录表，无临时分片目录
- 唯一的哈希是 `sha256(正文文本)`（`KnowledgeImportServiceImpl.java:709`），用于**内容增量去重**，不是文件秒传

**P1 — 后端阻塞式处理**

`DocServiceImpl.uploadDoc`（`:168-229`）在同一个请求线程内完成：落盘 → Tika 解析 → 入库 → RAG 分块 `docChunkService.indexDocument`。大文件时请求线程被长期占用，Tomcat 连接池容易被打满。

**P1 — 超长正文丢尾**

`KnowledgeImportServiceImpl.readContent()`（`:702`）对所有文档按 **UTF-8 纯文本**读取，PDF/DOCX 导入会得到乱码；并且超过 `maxContentChars` 的正文被静默 `substring` 丢弃。详见 §5。

**P2 — 已知隐患**

- `KnowledgeImportServiceImpl.readContent()`（`:702`）对所有文档按 **UTF-8 纯文本**读取，PDF/DOCX 导入会得到乱码
- `/uploads/**` 静态映射直出，若允许上传 `.html/.svg` 存在存储型 XSS 风险
- 应用层硬编码 `MAX_UPLOAD_BYTES = 50MB`（`DocServiceImpl.java:164`）与 yml 配置双头管理
- `:363` 的 `contentHash` 是在截断**之后**计算的，导致「60k 文档」和「它的 5 万前缀」会被增量去重判为相同。改方案时需改为对**全文**哈希。

## 2. 存储方案对比

### 2.1 选型前提：本次选型锚定的真实约束

**结论先行——脱离场景谈存储选型全是空话。** 本项目锚定「本地目录批量导入」这一具体场景，它的负载特征与「用户单个上传大文件」完全不同：

| 特征 | 目录批量导入 | 单文件上传 |
|---|---|---|
| 请求形态 | 一次操作产生 N 次写（N 可达 1 万+） | 1 次写 |
| 文件大小分布 | 长尾，90% 是 5KB~2MB 的小文件 | 通常较大 |
| 性能瓶颈 | **每文件固定开销**（元数据/RTT/事务） | 带宽 |
| 重复率 | **高**（同一份 PDF 散落多个目录） | 低 |
| 路径语义 | 目录路径 = 分类树，**必须保留** | 无 |

这四条里，「每文件固定开销」和「高重复率」是本次选型的胜负手。

### 2.2 候选方案全集（6 个）

| 编号 | 方案 | 形态 | 代表实现 |
|---|---|---|---|
| **方案一** | 本地文件系统 + DB 存路径 | 单机磁盘目录 | ext4 / XFS + `file_url` 字段 |
| **方案二** | 文件二进制存入数据库 | BLOB / LONGBLOB | MySQL InnoDB BLOB |
| **方案三** | 自建对象存储 | S3 兼容私有化集群 | **MinIO**、Ceph RGW |
| **方案四** | 云托管对象存储 | 公有云 SaaS | 腾讯云 COS、阿里云 OSS、AWS S3 |
| **方案五** | 分布式文件系统 | POSIX 语义共享文件系统 | **JuiceFS**、CephFS、GlusterFS、HDFS |
| **方案六** | 内容寻址 + 冷热分层（混合） | CAS 去重 + 本地热层 + 对象存储冷层 | 应用层 CAS + 方案一/三/四组合 |

> 方案三与方案四虽同属对象存储，但**运维成本与网络模型差异极大**（一个要自己扛 EC 与扩容，一个要扛 RTT 与账单），必须拆开评。方案六不是独立技术，而是把前面几种组合起来的**落地形态**，单列是因为它是最终推荐。

### 2.4 逐维度深度分析

#### 2.4.1 导入性能：瓶颈在「每文件固定开销」，不在带宽

**核心原理**：批量导入 10,000 个平均 200KB 的文件（共 2GB），带宽需求只有 2GB。任何一块 NVMe 都能在 2 秒内写完 2GB——**但实际耗时可能是 10 分钟**。差距全在每文件的固定开销上。

| 方案 | 单文件固定开销 | 主要成因 | 10,000 文件<br>串行耗时 | 并发 8 后<br>估算耗时 |
|---|---|---|---|---|
| 方案一 本地 FS | **0.1~0.3 ms** | `open`+`write`+`close` 系统调用；若每次 `fsync` 则升至 1~5ms | ~3 s | ~1 s |
| 方案二 DB BLOB | **8~30 ms** | 写放大 3×（redo log + binlog + 数据页）+ 事务锁 + 行外页分配 | ~200 s | ~40 s（且拖垮全库） |
| 方案三 MinIO（内网） | **1~3 ms** | HTTP 请求解析 + EC 编码 + 元数据落盘 | ~20 s | ~4 s |
| 方案四 云 OSS（同 VPC） | **5~15 ms** | 网络 RTT 主导 + 签名校验 | ~100 s | ~15 s |
| 方案四 云 OSS（公网） | **30~100 ms** | 公网 RTT + TLS 握手（长连接可摊薄） | ~600 s | ~80 s |
| 方案五 JuiceFS | **2~8 ms** | 元数据引擎一次事务（Redis/TiKV）+ 数据块上传 | ~40 s | ~8 s |
| 方案六 CAS 混合 | **0.1~0.3 ms**<br>命中去重时 **≈0** | 同方案一；重复文件直接返回已有 hash，**零字节写** | ~3 s<br>（30% 重复率 → ~2 s） | **<1 s** |

> 数字为量级估算，用于横向比较，不同硬件与配置会有偏差。

**三条容易被忽略的性能陷阱**：

1. **方案二不只是慢，它会污染全库**。InnoDB 的大 BLOB 字段会挤占 `innodb_buffer_pool`，把热点索引页刷出内存，导致**与上传毫不相关的查询集体变慢**。这个成本不体现在上传接口的耗时监控里——等你从慢查询日志发现问题时，迁移代价已经很高了。

2. **云对象存储有单前缀 QPS 限流**。主流云厂商对象存储的单一前缀通常有数千 QPS 的软上限。如果 CAS key 用 `2026/08/02/xxx` 这种时间前缀，批量导入会把请求全打在同一个前缀上触发限流。**正确做法是把 hash 的前 2~4 位放在路径最前面做散列**（`ab/cd/<full-hash>`），这也正好是 CAS 的天然形态。

3. **前端串行是最常见的真实瓶颈**。上面所有后端数字，在前端逐个 `await` 上传时都毫无意义——10,000 次串行 HTTP 请求，光是浏览器侧的排队就足以拖到几十分钟。**并发度 4~6 是必须的**（超过 6 收益递减，且浏览器对同域连接数有限制）。

**本维度结论**：方案六 ≥ 方案一 > 方案三 > 方案五 > 方案四 > 方案二。

#### 2.4.2 存储效率：原生方案全都不去重，唯一通用解是应用层 CAS

**空间利用率**

| 方案 | 冗余系数 | 小文件碎片 | 实际占用<br>（2GB 有效数据） |
|---|---|---|---|
| 方案一 本地 FS | 1.0×（无冗余，靠 RAID/备份） | ext4 块 4KB，1 万个 3KB 文件浪费 ~10MB | ~2.0 GB |
| 方案二 DB BLOB | ~3.0×（数据页+redo+binlog） | 页填充率不足 + 行外指针开销 | **~6 GB** |
| 方案三 MinIO EC(4+2) | 1.5× | 小于分片大小的对象不做 EC，退化为多副本 | ~3.0 GB |
| 方案四 云 OSS | 1.0×（**按有效字节计费**，冗余成本由厂商吸收） | 无 | ~2.0 GB |
| 方案五 三副本 DFS | 3.0× | 元数据引擎额外占用 | ~6.0 GB |
| 方案六 CAS + zstd | 1.0× ÷ 去重率 ÷ 压缩率 | 同方案一 | **~0.6 GB** |

**去重能力——这是本场景最大的省钱点**

必须说清一个事实：**上述前五种方案，原生都不提供跨文件去重**。
- 对象存储（MinIO / 云 OSS）不做内容去重，同一份文件传两次就是两份计费；
- JuiceFS/CephFS 也不做全局块级去重（JuiceFS 支持压缩，Ceph 的 dedup 仍属实验特性）；
- 文件系统层的 ZFS/Btrfs 去重需要巨量内存维护 DDT 表，生产环境普遍不建议开。

**所以去重必须在应用层做，方式就是 CAS（内容寻址存储）**：

```
物理 key = SHA-256(文件字节)
存储路径 = <hash[0:2]>/<hash[2:4]>/<hash>
```

同内容文件天然共用一份物理存储，通过引用计数管理生命周期。

这对目录导入的收益是**结构性**的——知识库目录里同一份 PDF/图片散落在多个子目录是常态，实测重复率常在 20%~40%。CAS 同时带来第二个红利：**秒传**。上传前先算 hash，命中已有对象则直接建立数据库关联，**零字节传输**。这一条同时改善了导入性能，两个维度一起赢。

再叠加压缩：Markdown/TXT/HTML 等文本类文件用 zstd 可再压 3~5×（PDF/图片/视频已压缩，不要重复压，白费 CPU）。

**本维度结论**：方案六 ≫ 方案四 > 方案三 ≈ 方案五 > 方案一 > 方案二。

#### 2.4.3 可扩展性：方案一有一堵硬墙，且比想象中来得早

**方案一的天花板不是磁盘容量，是「第二个后端实例」。**

这是最容易被低估的一点。单机跑的时候方案一毫无问题，但一旦为了高可用或负载均衡把后端扩到 2 个实例，就会立刻出现：

```
用户 → 负载均衡 → 实例 A（文件写入 A 的本地磁盘）
用户 → 负载均衡 → 实例 B（读取时找不到文件 → 404）
```

这个问题**无法通过加磁盘解决**，只能靠共享存储（NFS/DFS/对象存储）。也就是说，方案一的扩展天花板是**「必须单实例部署」**，通常在业务量增长到需要高可用时（远早于容量告急）就会撞上。

| 方案 | 容量上限 | 横向扩展方式 | 硬约束 |
|---|---|---|---|
| 方案一 | 单机磁盘（数 TB） | 只能纵向加盘 | **必须单实例**；单目录文件数超 10 万后 ext4 htree 检索退化 |
| 方案二 | 受 DB 实例上限 | 分库分表（极痛，BLOB 无法按业务键均匀切） | 单表 BLOB 超百 GB 后 DDL 几乎不可执行 |
| 方案三 MinIO | 单集群 PB 级 | 加节点扩 Server Pool | 扩容需新建 Pool，已有数据不自动再平衡 |
| 方案四 云 OSS | 实质无限 | 厂商托管，零操作 | 单前缀 QPS 限流；跨云迁移有出网流量成本 |
| 方案五 DFS | PB 级 | 加数据节点 | **元数据引擎是瓶颈**（JuiceFS 用 Redis 时元数据全内存，亿级文件需数百 GB 内存） |
| 方案六 | 取决于底层实现 | **换 StorageService 实现即可**，业务代码零改动 | 需前期做好抽象 |

**方案六的扩展性得分（★★★★）来自架构而非技术**：CAS 层与物理存储层解耦后，从本地磁盘切到 MinIO 再切到云 OSS，是替换一个 Spring Bean 的事，数据迁移就是一次 `rsync`/`mc mirror`——因为 CAS 的 key 是内容哈希，**在任何后端都是同一个 key**，天然可迁移、可校验、可比对。

**本维度结论**：方案四 > 方案三 ≈ 方案五 ≈ 方案六 > 方案一 ≈ 方案二。

#### 2.4.4 备份恢复：真正的难点是「文件与 DB 的一致性对齐」

分开备份文件和数据库，会引入一个方案二天然没有的问题：**两个备份点的时间戳不一致**。

```
T1  备份数据库    → 含文档记录 #1001
T2  上传新文件     → 落盘 file-X
T3  备份文件目录   → 含 file-X，但 DB 备份里没有 #1002 的记录
     恢复后：file-X 成为孤儿文件（占空间，无人引用）
     反向场景：DB 记录存在但文件缺失 → 用户点下载 404（更严重）
```

| 方案 | 备份方式 | RPO | RTO（1TB） | 一致性 | 灾难恢复难度 |
|---|---|---|---|---|---|
| 方案一 | rsync / LVM·ZFS 快照 | 小时级 | 数小时（受磁盘 IO 限制） | **需应用层对账** | 高：异地容灾要自己搭 |
| 方案二 | mysqldump / xtrabackup | 分钟级 | **极长**（1TB dump 恢复可达 10+ 小时） | **天然强一致** ✓ | 中：一份备份搞定，但体积巨大 |
| 方案三 MinIO | 版本控制 + `mc mirror` 跨集群 | 分钟级 | 中等（可并行拉取） | 需对账 | 中：需自建异地集群 |
| 方案四 云 OSS | 版本控制 + 跨区复制 + 生命周期归档 | **近 0** | 短（无需恢复，直接读） | 需对账 | **低**：厂商提供 12 个 9 持久性 |
| 方案五 DFS | 副本/EC + 快照 | 小时级 | 中等 | 需对账 | 高：**副本 ≠ 备份**（误删会同步删除所有副本） |
| 方案六 | 继承底层 + **CAS 自校验** | 同底层 | 同底层 | **可自动对账** ✓ | 中低 |

**方案二在这个维度确实赢**——它是唯一一个「一次 dump 恢复出完整一致状态」的方案，这是它唯一真正的优势。但它赢的这一局，用工程手段完全可以补齐：

1. **写入顺序：先文件后事务**。文件落盘成功才提交 DB 事务。这样失败只会产生孤儿文件（可回收），永远不会产生「DB 有记录但文件缺失」（不可恢复的用户可见错误）。
2. **对账任务**：每日扫描 CAS 目录与 `sys_file_object` 表双向比对。孤儿文件移入 `.trash/` 保留 7 天再删（**不要直接删**，误判代价太高）；缺失文件标记 `status=BROKEN` 并告警。
3. **CAS 天然自校验**：文件名就是内容哈希，重算一遍 SHA-256 即可验证完整性，静默损坏（bit rot）能被立刻发现——这是普通路径存储做不到的。

**本维度结论**：方案四 > 方案二 ≈ 方案三 ≈ 方案六 > 方案五 > 方案一。

#### 2.4.5 运维成本：部署复杂度 + 日常开销 + 人力

| 方案 | 部署复杂度 | 日常维护 | 需要的技能 | 1TB 年成本（估算） |
|---|---|---|---|---|
| 方案一 | **零**（建个目录） | 磁盘告警、备份脚本 | 无 | 硬件折旧，~几百元 |
| 方案二 | 零（无新组件） | **DB 运维压力剧增**：备份变慢、主从延迟、大事务 | DBA | DB 存储通常更贵，~数千元 |
| 方案三 MinIO | **中高**：生产需 4 节点起做 EC，TLS 证书、版本升级、纠删码配置 | 节点健康、容量再平衡、升级（MinIO 迭代快，有破坏性变更史） | 分布式存储基础 | 硬件 + 人力，人力是大头 |
| 方案四 云 OSS | **低**：开个桶、配 RAM 子账号和 CORS | 几乎为零，看账单 | 云平台基础 | 存储 ~1,500 元/年 + 请求费 + **出网流量费（最容易超支）** |
| 方案五 DFS | **最高**：Ceph 需专职团队；JuiceFS 轻些但要额外维护元数据引擎（Redis/TiKV）的高可用与备份 | 元数据引擎扩容、慢盘剔除、故障域规划 | **专职存储工程师** | 人力成本远超硬件 |
| 方案六 | **低**（起步阶段等同方案一） | 多一个对账定时任务 | 无 | 起步 ≈ 方案一 |

**两个高频踩坑点**：
- **云 OSS 的出网流量费**是最容易失控的项。如果后端做中转（用户 → 后端 → OSS → 后端 → 用户），流量翻倍计费且后端带宽成为瓶颈。**必须用预签名 URL 让客户端直传/直读**。
- **MinIO 单机模式不做 EC**，只是个 S3 协议的本地目录包装。用它当生产会同时失去方案一的简单性和方案三的可靠性——是两头不讨好的配置。

**本维度结论**：方案一 > 方案二 ≈ 方案四 ≈ 方案六 > 方案三 > 方案五。

### 2.5 方案二（DB BLOB）的修正与现实约束

切到 MySQL 8.0 后，方案二（BLOB 入库）**不再是技术不可行**，需如实修正此前「3 倍写放大、缓冲池必爆」的偏激说法：
- MySQL 8.0 默认 `DYNAMIC` 行格式：大 BLOB 只把前 768 字节（实际 20 字节指针）放聚簇索引，主体存 **off-page**，缓冲池污染远小于旧格式；
- InnoDB redo log **不记录 BLOB 主体**，只是页变更，因此存储端写放大没有之前说的那么夸张。

但即便可行，本项目仍应避开 BLOB，理由更务实：

1. **决定性的现实约束：方案二在当前技术栈下不可运行**。项目当前用的是 **H2 内存数据库**（`application.yml:12`，`jdbc:h2:mem:`）。BLOB 入库意味着**所有文件字节常驻 JVM 堆内存**，导入几个 PDF 就会 OOM。方案二不是「性能差一些」，而是**在现有技术栈下根本不可运行**——这一条比前面所有理论分析都更硬。

2. **备份膨胀**：`mysqldump` 把 BLOB base64 编码，dump 文件体积 +30% 以上，恢复慢；个人备份从「拷文件夹」变成「导库」，心智负担陡增。

3. **`max_allowed_packet` 暗坑**：必须调大到大于你最大的单个文件，否则大文件静默失败。

4. **文件不可直接操作**：没法 `ls`/`cp`/`rsync`/`open`，所有访问被绑死在应用内。

5. **导入速度**：文件流式落盘（走 OS page cache）天然快于「经 MySQL 协议 → base64 解码 → 入行」。批量导目录时差距明显。

> 6 项排名中方案二垫底，且当前 H2 内存库下不可运行。仅在「文件总量 < 1GB 且强一致性压倒一切」的场景下可考虑，本项目不符合。

### 2.6 规模分界线

| 总存储量 | 单文件典型大小 | 推荐方案 |
|---|---|---|
| **< 1GB** | < 1MB | 方案二**可以接受**（运维最省事，**H2 内存库下不可用**），或方案一 |
| **1GB ～ 100GB** | 1MB ～ 500MB | ✅ **方案六：本地 FS + CAS + 抽象层** ← KnowFlow 当前位置 |
| **100GB ～ 10TB** | 任意 | 方案六进阶：**MinIO 自建对象存储**，DB 存 objectKey |
| **> 10TB / 多地域 / 需 CDN** | 任意 | 方案六 + 云对象存储（OSS / COS）+ **前端预签名 URL 直传**，服务端不过流量 |

**特例补充**：
- 单个 < 64KB 的小文件（头像、图标、缩略图）入库反而更划算——省一次磁盘 IO，且不产生海量小文件拖垮 inode
- 强合规场景（电子签章、审计留痕、法律证据）可以为**一致性牺牲性能**选方案二
- 文档**正文文本**继续存 `content LONGTEXT`（详见 §5），只有**原始二进制文件**走文件存储

## 3. 推荐方案：方案六

### 3.1 总述

**最优方案：方案六 —— 本地文件系统 + CAS 内容寻址 + `StorageService` 抽象层**

即：**以方案一为物理底座，叠加内容寻址去重，并用一层存储抽象为未来切换 MinIO / 云 OSS 预留通道。**

### 3.2 五条理由（逐维度对应）

**理由一（导入性能，权重 25%）**：目录批量导入的瓶颈是每文件固定开销，本地 FS 的 0.1~0.3ms 是所有方案中最低的，比 MinIO 快约一个数量级，比云 OSS 快约两个数量级。叠加 CAS 秒传后，重复文件的开销降到「一次 hash 计算 + 一行 DB insert」，**零字节写入**。这是全场唯一能同时拿满导入性能与存储效率两项的方案。

**理由二（存储效率，权重 15%）**：目录导入场景的文件重复率通常在 20%~40%，CAS 去重是直接的空间节省，而这是对象存储和分布式文件系统**原生都不提供**的能力——既然去重无论如何都要在应用层做，那么先做去重、再谈底层换什么，顺序上更划算。

**理由三（可扩展性，权重 25%）**：方案一单独使用的致命伤是「必须单实例部署」，但这个伤害由 `StorageService` 抽象层化解。CAS 的 key 是内容哈希，在任何后端都是同一个 key，迁移 = `mc mirror` + 换一个 Bean 实现，**业务代码零改动、数据可逐一校验**。用一天的抽象成本，换掉了方案一唯一的硬伤。

**理由四（备份恢复，权重 20%）**：方案二的强一致优势通过「先文件后事务 + 每日双向对账 + `.trash` 保留期」补齐；同时 CAS 自带完整性自校验（重算哈希比对文件名），这是方案二和普通路径存储都没有的额外能力。

**理由五（运维成本，权重 15%）**：起步阶段的运维开销等同方案一（近乎为零），只多一个定时对账任务。相比 MinIO 需要 4 节点起步、JuiceFS 需要额外维护元数据引擎高可用，对当前团队规模而言，这是唯一不需要引入新运维负担的选择。

### 3.3 演进路线与切换触发条件

| 阶段 | 数据规模 / 触发条件 | 采用方案 | 迁移动作 |
|---|---|---|---|
| **当前** | < 100 GB，单实例 | 方案六（本地 CAS） | 无 |
| **触发点 A** | 后端需扩到 **2 个实例**（高可用） | 方案六 + MinIO 后端 | `mc mirror` 一次 + 换 Bean |
| **触发点 B** | > 500 GB 或需异地容灾 | 方案六 + MinIO 集群 EC(4+2) | 同上 |
| **触发点 C** | 整体上云 | 方案六 + COS/OSS（预签名直传） | 同上 |

> **触发点 A 通常先于 B 到来**——扩展压力来自可用性需求，不是容量需求。这也是为什么抽象层要**现在**做，而不是等磁盘快满了再做。

### 3.4 个人本地部署的简化视角

针对**个人本地单机使用**场景（非多人/非云部署，愿意把存储从 H2 改为 MySQL），可对方案六做**减配**：

- **物理底座保持方案一**：本地文件系统存文件实体 + MySQL 只存路径与元数据。
- **CAS 只取「前端 hash + 落盘前查重」一招**：若你的知识库目录里同一 PDF 散落多个子目录（常见），可在 `doc_document` 加 `file_hash` + 引用计数，重复文件只存一份。**但不用上每日对账定时任务**——个人用，手动跑一次去重脚本即可。
- **极薄的 `StorageService` 抽象层**（可选）：定义 `save(InputStream, hash) / get(path) / delete(path)`，默认实现是本地 FS；将来真要上云，换一个 Bean 即可，业务代码零改。不增加多少成本，给将来留退路。
- **分片上传 / 断点续传：个人本地基本不需要**。localhost 上传稳定性极高，分片只增加复杂度。只有当你要导 **>2GB 的单个大文件** 时才考虑加分片；届时协议复用 §4 的四段式即可，但属可选增强而非必需。
- **不要**为个人本地用上：DB BLOB、MinIO、CAS 去重对账那套重型方案。

一句话：**个人本地 + MySQL：文件落本地磁盘、路径存 MySQL、逐文件并发上传带真进度条**。BLOB/MinIO/CAS 重型方案一律不上，保持简单 = 最快也最好维护。

### 3.5 明确不推荐

- **方案二（DB BLOB）**：6 项排名垫底，且当前 H2 内存库下不可运行。仅在「文件总量 < 1GB 且强一致性压倒一切」的场景下可考虑，本项目不符合。
- **方案五（分布式 FS）**：技术上可行，但对当前规模是**严重过度设计**。Ceph 需要专职存储工程师；JuiceFS 虽轻量，但要额外维护元数据引擎的高可用与备份，等于用一个新的单点风险换扩展性。在 PB 级或强 POSIX 语义需求出现前不必考虑。
- **方案四单独使用（不加抽象层）**：会把云厂商 SDK 侵入业务代码，未来迁移成本极高；且公网直连场景下导入性能是本地的 1/100 量级。

## 4. 上传优化（分片 / 断点续传 / 秒传）

### 4.1 目标（可验收）

| 指标 | 现状 | 目标 |
|---|---|---|
| 单文件上限 | 50MB | **2GB** |
| 单批文件数 | 无限制（实际 500MB 即崩） | **10000 个 / 无总量上限** |
| 进度准确度 | 0%（假进度） | **误差 < 1%，含速率 + ETA** |
| 断网恢复 | 全部重传 | **续传，已传分片不重复** |
| 重复文件 | 完整重传 | **秒传，< 200ms 完成** |
| 后端内存 | 随文件大小增长 | **恒定（流式，与文件大小无关）** |
| 局部失败影响面 | 整批作废 | **仅失败文件可单独重试** |

### 4.2 分片上传协议设计

#### 4.2.1 四段式流程

```
① init   → 算 hash，问服务端「传过没 / 传到哪了」
② chunk  → 并发传缺失分片（可暂停、可重试）
③ merge  → 服务端顺序合并 + 整文件校验
④ async  → 解析 / 入库 / RAG 索引异步化，前端轮询或 SSE
```

#### 4.2.2 接口定义

统一前缀 `/api/upload`，均需 JWT（**记得在 `SecurityConfig` 中显式配置，本项目只放行白名单 GET**）。

**`POST /api/upload/init`**

```json
// 请求
{
  "fileHash": "a3f5...(64位 SHA-256)",
  "fileName": "深度学习.pdf",
  "fileSize": 734003200,
  "chunkSize": 5242880,
  "categoryId": 12,
  "relPath": "AI/机器学习/深度学习.pdf"
}
// 响应
{
  "uploadId": "5f2c8a...",
  "instant": false,          // true = 秒传命中，直接跳到完成态
  "docId": null,             // 秒传时返回已建好的文档 id
  "uploadedChunks": [0,1,2,7]  // 断点续传：已存在的分片索引
}
```

**幂等**：同一 `(fileHash, userId)` 重复 init 返回同一个 `uploadId`，这就是断点续传的入口。

**`POST /api/upload/chunk`**

`multipart/form-data`：`uploadId` + `index` + `chunk`(MultipartFile)。
服务端写入 `{uploadDir}/chunks/{fileHash}/{index}.part`，更新任务位图。**先校验 index 范围与 uploadId 归属，防越权写入。**

**`POST /api/upload/merge`**

```json
{ "uploadId": "5f2c8a..." }
// 响应
{ "fileUrl": "/uploads/2026/08/02/uuid.pdf", "docId": 3312, "parseStatus": "PARSING" }
```

合并用 `FileChannel.transferTo` 顺序追加（零拷贝），合并完**重算整文件 SHA-256 比对**，不一致则回滚并要求重传。校验通过后删除 `chunks/{fileHash}/` 目录。

**`GET /api/upload/status?uploadId=xxx` / `DELETE /api/upload/{uploadId}`**

分别用于查询进度（含服务端解析阶段）和主动取消 + 清理碎片。

### 4.3 关键参数

| 参数 | 取值 | 依据 |
|---|---|---|
| 分片阈值 | 10MB | 小文件分片得不偿失，直接走现有 `/docs/upload` |
| 分片大小 | 5MB（自适应：>1GB 用 20MB） | 控制分片总数 < 10000，避免元数据爆炸 |
| 并发数 | 3 | 浏览器同域 6 连接上限，留 3 条给其他请求 |
| 重试 | 3 次，指数退避 1s/2s/4s | — |
| 碎片过期 | 24h | 定时任务扫 `status=0 AND expire_time < now()` 清目录 |
| `max-file-size` | 调至 **10MB** | 分片后单请求变小，反而可以收紧，提升安全性 |

### 4.4 哈希计算（前端）

不能 `FileReader.readAsArrayBuffer(整个文件)` —— 2GB 文件直接爆内存。两个方案：

- **精确哈希**：`hash-wasm` 的增量 SHA-256，边切片边喂，放进 **Web Worker** 避免卡 UI。2GB 约 8～15 秒。
- **抽样哈希**（推荐默认）：`SHA256(首2MB + 中间2MB + 尾2MB + fileSize)` 作为秒传探测键，命中后服务端再做一次全量校验。2GB 耗时 < 300ms。

界面上把哈希阶段单独做成「校验中」状态，不要混进上传进度里。

### 4.5 前端进度条设计

#### 4.5.1 三级进度模型

```
批次进度 = Σ(各文件已传字节) / Σ(各文件总字节)
文件进度 = (已完成分片数 × chunkSize + Σ在途分片的 loaded) / fileSize
分片进度 = axios onUploadProgress 的 e.loaded
```

关键：用 `Map<chunkIndex, loadedBytes>` 记录在途分片，每次回调更新后重算文件进度。**不能简单用「完成分片数 / 总分片数」**——3 并发时进度条会一卡一跳。

#### 4.5.2 状态机（UI 必须区分）

```
排队中 → 校验中(hash) → 上传中(x%) → 合并中 → 解析中 → 完成
                              ↓            ↓
                          已暂停 ←→      失败(可重试)
```

现状把「上传」和「后端解析」混在一个动画里，是用户觉得卡死的根因。解析阶段单独展示，配合异步化后的轮询/SSE。

#### 4.5.3 展示信息

单文件行：`文件名 | 进度条 | 42% | 218MB/512MB | 3.2MB/s | 剩余 1分32秒`
速率用**滑动窗口 EMA**（近 5 秒），瞬时值抖动太大不可读。

#### 4.5.4 暂停 / 续传

- 暂停：`AbortController.abort()` 取消在途分片请求，已完成分片保留在服务端
- 恢复：重新 `init` → 拿 `uploadedChunks` → 只传缺失的
- **刷新页面后**：用 IndexedDB 存 `{fileHash, uploadId, relPath}`，但浏览器安全策略下 `File` 对象**无法持久化**，用户必须重新选择同一文件/目录；重选后按 hash 自动匹配并跳过已传分片。这个限制要在 UI 上讲清楚，不要假装能全自动恢复。

### 4.7 后端解析异步化

`merge` 立即返回 `docId` + `parseStatus=PARSING`，Tika 解析与 RAG 分块投递到线程池（**按阿里规约用 `ThreadPoolExecutor` 显式构造，禁用 `Executors`**）。这样：
- 300s 超时问题消失
- Tomcat 请求线程不被长期占用
- 前端可以显示「已上传，正在解析 3/128 篇」

1. 新建 `application-mysql.yml`（或改 `application.yml` 的 `spring.datasource`）：

   - `url: jdbc:mysql://localhost:3306/knowflow?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai`

3. **校验 `schema.sql` 在真 MySQL 可跑**：当前为 H2 `MODE=MySQL` 兼容写法，需注意 `AUTO_INCREMENT`、布尔 `TINYINT`、索引定义等是否与 MySQL 完全一致（建议先在本地 MySQL 跑一遍建表验证）。
4. 应用层把「物理路径」与「用户目录树」解耦：落盘用扁平目录（如 `uploads/<yyyyMM>/<uuid>.<ext>`），目录结构只存 DB（`doc_category` + 新增 `relative_path` 列），避免同名覆盖 / 路径穿越 / 单目录文件过多。

## 5. 超长正文存储方案

### 5.1 现状（实测，决定方案是否成立）

> 适用前提：个人本地单机部署 + MySQL 存储（见 §3.4）。本节在用户提出的四种方案基础上，结合实际代码现状给出落地建议。

| 项 | 现状 | 证据 |
|---|---|---|
| 截断阈值 | 导入时默认 `maxContentChars = 50000` 字符 | `KnowledgeImportController.java:69/107`；`KnowledgeImportOptionsDTO.java:48` |
| 截断逻辑 | `if (content.length() > maxChars) content = substring(0, maxChars) + "\n\n...(正文已截断)"` | `KnowledgeImportServiceImpl.java:339-341` |
| **超出部分去向** | **直接丢弃，无任何保留** | 同上，仅 `substring` 不落库 |
| `content` 字段类型 | `TEXT` | `schema.sql:28` |
| 列表预览 | 列表接口已把 `content` 截断到 4000 字符做预览 | `DocServiceImpl.java:461/486`（与导入截断是两处独立逻辑） |
| AI/抽取侧截断 | 送给 LLM 的上下文另有 20000（`AiServiceImpl.java:137`）/ 实体抽取 6000（`KnowledgeService.java:771`）上限 | 与导入截断解耦，应保留 |

### 5.2 切 MySQL 的强制前提（迁移雷区）

当前项目跑在 H2（`MODE=MySQL`），H2 的 `TEXT`/`CLOB` 实际不受 64KB 限制，所以现在一切正常。但一旦切到**真 MySQL**，`TEXT` 类型硬上限是 **65,535 字节**（UTF-8MB4 下约 16,383~21,845 字符）。这意味着：

- 连「截断到 5 万字符」的结果都**塞不进 `TEXT`**——MySQL 会按字节静默截断（SQL 模式非严格时）或直接报错（严格模式）；
- 因此 **`content TEXT` → `LONGTEXT` 不是方案四的「可选优化」，而是切 MySQL 的强制前提**。不做这步，所有超长文档在 MySQL 上都会丢尾。

另：`:363` 的 `contentHash` 是在截断**之后**计算的，导致「60k 文档」和「它的 5 万前缀」会被增量去重判为相同。改方案时需改为对**全文**哈希。

### 5.3 四种方案评估

#### 方案一：分段存储（主表 + 子表）
- 主表 `doc_document.content` 存前 `maxContentChars`；新增 `has_more TINYINT`；子表 `doc_document_segment(doc_id, seq, content, char_count)`。
- **优点**：主表结构基本不变；预览快（列表只取前段）；全文仍在 DB 内，详情/检索都能还原；`has_more` 让前端按需再拉后续段。
- **缺点**：新增子表 + 写入/读取/拼接三段逻辑；需事务保证主表与分段一致（要么全写要么全回滚）。
- **适用**：希望全部内容留在库内、又要列表轻量。

#### 方案二：摘要 + 原文外链
- `content` 存截断预览 + 末尾提示；新增 `full_content_path` 指向磁盘/对象存储上的完整 `.md`；前端「查看完整文档」按钮。
- **优点**：主表字段最干净；不碰 DB 大字段；与「文件落本地磁盘」的存储决策天然一致（原文本来就该在磁盘上）。
- **缺点**：DB 内不可直接搜超出部分（除非搜索引擎）；依赖文件路径可用性（删文件即失效）。
- **适用**：超长文档仅存档、偶尔看全文；且已按存储方案把原文落盘。

#### 方案三：全文索引外置（ES / Meilisearch）
- `content` 存截断预览；完整文本进搜索引擎，关联 `doc_id`；列表走 DB、搜索/详情走引擎。
- **优点**：搜索能力跃升，彻底摆脱字段长度与 DB 查询压力。
- **缺点**：引入额外组件、数据同步链路、运维成本。**对个人本地严重过度设计。**
- **适用**：多人/生产、强搜索需求。**不推荐本场景。**

#### 方案四：字段类型扩容（TEXT → LONGTEXT）
- `content` 改为 `LONGTEXT`（MySQL 上限 4GB），移除应用层 50000 截断，仅做文件大小校验（如 ≤10MB）。
- **优点**：**零新增表、零分段逻辑、一劳永逸、不丢任何数据**；列表接口本就只回 4000 字预览，不受影响。
- **缺点**：单字段可达数 MB；若未来做「列表批量带回 content」会涨 payload——但本项目列表已截断，无此问题；需配 `max_allowed_packet` > 最大文档。
- **适用**：**个人本地 MySQL 的最轻量解**。

### 5.4 推荐组合（针对个人本地 + MySQL）

#### 必做前提（不可省略）
1. `doc_document.content` 由 `TEXT` 改为 **`LONGTEXT`**（否则 MySQL 静默截断）。
2. 校验 `max_allowed_packet`（MySQL 默认 64MB）> 你允许的最大单文档（建议设 `max_allowed_packet=64M`，对应 ≤ ~16MB 的 Markdown）。

#### 路线 A（最轻量，推荐首选）：纯方案四
- 改 `LONGTEXT` + **去掉导入侧的 50000 截断**（保留 AI 侧 20000/6000 截断不变）。
- 新增 `content_hash` 改为对**全文**计算，保证增量去重正确。
- **零新表、零分段逻辑、不丢数据**，对个人单机完全够快。
- 代价：单文档上限由「字符数」变为「文件大小」（如 ≤10MB）。

#### 路线 B（要列表轻量 + 全文在库）：方案一 + 方案四
- `LONGTEXT` 前提下，仍按 `maxContentChars` 在**应用层**把正文拆成「主表前段 + `doc_document_segment` 后续段」，`has_more` 标记。
- 好处：详情页/检索能还原完整正文，列表只取前段，DB 行不变胖。
- 适合「既想预览快、又不想丢超长内容」的偏好。

#### 为什么本场景不推方案三
个人本地跑 ES/Meilisearch 是杀鸡用牛刀；方案二/四已覆盖「存档」与「不失真」需求。

#### 决策表

| 你的诉求 | 推荐 |
|---|---|
| 个人用、要最简单、不丢数据 | **路线 A：方案四（LONGTEXT + 去截断）** |
| 列表要轻 + 全文留库内 | **路线 B：方案一 + 方案四** |
| 超长仅存档、已落盘原文 | 方案二（外链，复用存储层） |
| 强搜索/多人 | 方案三（不在本场景） |

## 6. 落地设计

### 6.1 `StorageService` 抽象层（一次抽象，四种实现可切）

```java
/**
 * 文件存储服务 SPI。
 * 所有实现均以内容哈希（SHA-256）作为对象 key，保证跨后端可迁移、可校验。
 */
public interface StorageService {

    /**
     * 存入字节流，返回内容哈希。若内容已存在则直接返回，不重复写入（秒传）。
     *
     * @param in          输入流
     * @param sizeBytes   字节数，用于预分配与校验
     * @return 内容哈希（SHA-256 十六进制小写，64 字符）
     */
    String put(InputStream in, long sizeBytes);

    /** 判断内容是否已存在，用于上传前秒传探测。 */
    boolean exists(String contentHash);

    /** 读取对象；调用方负责关闭流。 */
    InputStream get(String contentHash);

    /** 物理删除对象。仅当引用计数归零时由回收任务调用，业务层禁止直接调用。 */
    void delete(String contentHash);

    /** 生成临时访问 URL；本地实现返回受控下载端点，对象存储实现返回预签名 URL。 */
    String presignedUrl(String contentHash, Duration ttl);
}
```

实现类：`LocalFsStorageService`（现在用）→ `MinioStorageService` → `CosStorageService`。切换只改一处 `@ConditionalOnProperty`，业务代码零感知。

> 个人本地版可极薄化：定义 `save(InputStream, hash) / get(path) / delete(path)`，默认实现是本地 FS；将来真要上云，换一个 Bean 即可。

### 6.2 物理路径与逻辑路径必须解耦（目录导入的必答题）

**绝对不要直接按用户原目录结构落盘。** 这是目录批量导入最容易埋雷的地方：

| 风险 | 后果 |
|---|---|
| 不同目录下同名文件 | 相互覆盖，数据丢失 |
| 路径超长 | Linux 单文件名上限 255 字节，中文 UTF-8 占 3 字节 → 85 个汉字即超限 |
| 非法字符 `: * ? " < > \|` | 跨平台写入失败 |
| 路径穿越 `../../etc/passwd` | **严重安全漏洞**，可写任意路径 |
| 单目录文件数 > 10 万 | ext4 htree 索引检索性能显著退化 |

**正确做法——两层解耦**：

```
物理层（存储用，扁平化 CAS）
  {upload.dir}/cas/ab/cd/abcd1234...ef.bin      ← 天然分桶，单目录最多 256 个子目录

逻辑层（展示用，存数据库）
  doc_document.file_name      "第3章-索引原理.pdf"      原始文件名
  doc_document.category_path  "/数据库/MySQL/进阶"       目录树映射的分类路径
  doc_document.file_hash      "abcd1234...ef"           指向物理层
```

用户看到的是原始目录结构（从 DB 渲染），磁盘上是扁平哈希桶。**同时规避上表全部 5 项风险**，并让 CAS 去重成为可能。

### 6.3 表结构增量 DDL（合并版）

遵循阿里规约：逻辑外键（无物理 FK）、逻辑外键列建索引、**唯一索引不含 `deleted` 列**。

### 6.4 批量导入吞吐优化清单

| 优化项 | 做法 | 预期收益 |
|---|---|---|
| 前端并发 | 并发度 4~6 逐文件上传，替代整目录单次 FormData | 消除 413 整批失败风险 |
| 秒传探测 | 上传前 `POST /api/files/check` 批量传 hash 列表，命中的跳过 | 重复率 30% → 省 30% 传输 |
| 批量入库 | `saveBatch(list, 1000)` 替代逐条 insert | DB 往返减少约 1000× |
| 分类树缓存 | 复用现有 `dirCategoryCache`（`KnowledgeImportServiceImpl:421`） | 避免重复查询分类 |
| 异步解析 | 落盘即返回，正文提取/向量化进异步队列 | 接口响应从秒级降至毫秒级 |
| 哈希计算位置 | 前端 Web Worker 算 SHA-256，避免阻塞 UI 主线程 | 页面不卡顿 |

### 6.5 顺带必须修的两个 Bug

1. **`KnowledgeImportServiceImpl:702` 的 `readContent()` 按 UTF-8 纯文本读取所有文件**——PDF/DOCX 导入后正文是乱码。落地存储改造时应同步接入 Apache Tika 或 PDFBox + POI 做格式化提取，否则「文件存下来了但内容不可用」，存储方案再优也没有意义。
2. **`contentHash` 在截断之后计算**（`:363`）——导致「60k 文档」和「它的 5 万前缀」被增量去重判为相同。改方案时改为对**全文**哈希。

## 8. 风险与反模式

### 8.1 反模式速查

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| `uploads/` 放在 jar 同级或容器可写层 | **容器重启文件全丢** | Docker 必须 volume 挂载到宿主机或网络存储 |
| MinIO 单机模式当生产 | 无 EC 保护，同时失去方案一的简单性 | 生产 4 节点起，或直接用云 OSS |
| 云 OSS 后端中转上传 | 流量双倍计费 + 后端带宽成瓶颈 | 预签名 URL 客户端直传/直读 |
| CAS 对象直接物理删除 | 其他文档仍引用 → 集体 404 | 引用计数归零 + `.trash/` 保留 7 天 |
| 对账发现孤儿文件立即删 | 误判导致不可逆数据丢失 | 一律先移入 `.trash/`，过保留期再清 |
| 用 `content_hash` 做秒传 | 语义错误：它是**正文文本**哈希，不是文件字节哈希 | 新增 `file_hash` 字段专用于秒传 |
| 把用户原路径直接拼进磁盘路径 | 路径穿越漏洞 + 重名覆盖 | 物理层 CAS 扁平化，逻辑层存 DB |
| 唯一索引含 `deleted` 列 | 逻辑删除后重复上传撞唯一键报 500（`uk_app_user_goal` 事故同类） | 唯一索引只用业务键；清理走物理删除 |
| `doc_document.content` 保持 `TEXT` 类型切 MySQL | 超长文档被静默截断丢尾 | 切 MySQL 前必改 `LONGTEXT` |
| `contentHash` 对截断后的正文计算 | 60k 文档与它的 5 万前缀被增量去重判为相同 | 改为对**全文**哈希 |

### 8.2 已知坑（本项目实测）

| 风险 | 应对 |
|---|---|
| 唯一索引含 `deleted` 列 → 重复上传撞唯一键报 500 | `uk_fut_upload_id` / `uk_sfo_hash` 只用业务键；清理走**物理删除** |
| Tomcat `MultipartFile.transferTo()` 相对路径 bug | 继续沿用 `UploadHelper` 的 `Files.copy(InputStream, path)` |
| H2 内存库重启数据清零，`chunks/` 目录残留 | 应用启动时清理孤儿分片目录 |
| 新接口被 `SecurityConfig` 拦截 401 | 本项目只放行白名单 GET，写接口需登录——需显式配置 |
| 多实例部署时分片散落在不同机器 | 分片目录必须落共享存储，或网关做 `uploadId` 一致性哈希 |
| 上传 `.html/.svg` 经 `/uploads/**` 直出造成存储型 XSS | 扩展名白名单 + 响应头 `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff` |
| 前后端端口错位（会话注入随机 `SERVER__PORT`） | 后端强制 `--server.port=8080`，前端 `SERVER__PORT=8080` |

## 9. 决策速查表

### 9.1 存储方案

| 你的情况 | 选择 |
|---|---|
| 文件总量 < 1 GB，且强一致压倒一切，且用的是磁盘型 DB | 方案二尚可（**H2 内存库下不可用**） |
| 单实例部署，< 100 GB —— **KnowFlow 当前位置** | **方案六：本地 CAS + 抽象层** ✓ |
| 需要多实例 / 高可用，100 GB ~ 10 TB | 方案六 + MinIO 集群 |
| 已上云，或需要 CDN 加速与异地容灾 | 方案六 + 云 OSS 预签名直传 |
| PB 级，或需要 POSIX 语义供大数据组件直读 | 方案五（JuiceFS/CephFS），需配专职运维 |
| 头像、图标等 < 64 KB 的小图 | 入库反而更划算（省一次 IO 与一次 HTTP） |
| 文档正文文本 | 继续存 `content LONGTEXT`，只有**原始二进制**走文件存储 |

### 9.2 个人本地部署（简化版）

| 你的诉求 | 选择 |
|---|---|
| 个人本地单机 + 愿切 MySQL | **方案一简化版**：文件落本地磁盘、路径存 MySQL、逐文件并发上传带真进度条 |
| 知识库目录有重复文件 | CAS 简化版：`doc_document` 加 `file_hash` + 引用计数，手动跑一次去重脚本（不上每日对账定时任务） |
| 单文件 > 2GB 才需要分片 | 加分片协议（复用 §4 四段式，可选增强） |

### 9.3 超长正文

| 你的诉求 | 推荐 |
|---|---|
| 个人用、要最简单、不丢数据 | **路线 A：方案四（LONGTEXT + 去截断）** |
| 列表要轻 + 全文留库内 | **路线 B：方案一 + 方案四** |
| 超长仅存档、已落盘原文 | 方案二（外链，复用存储层） |
| 强搜索/多人 | 方案三（不在本场景） |

## 11. 一句话总结

**推荐方案六**：以本地文件系统为物理底座（拿满导入性能与最低运维成本），叠加 CAS 内容寻址补齐去重与秒传（拿满存储效率），再用 `StorageService` 抽象层化解方案一「必须单实例」的硬伤（拿回可扩展性）。加权总分 4.40 分居首，且是唯一一个**起步成本接近零、演进路径不需要重写业务代码**的方案。

方案二在当前 H2 内存库技术栈下不可运行；方案五对当前规模属于严重过度设计；方案三/四是未来的演进目标，而非现在的起点。

个人本地 + MySQL 简化版：**文件落本地磁盘、路径存 MySQL、逐文件并发上传带真进度条**；切 MySQL 前必把 `content` 改为 `LONGTEXT` 并对全文计算 `contentHash`。BLOB/MinIO/CAS 重型方案一律不上，保持简单 = 最快也最好维护。
