# 多语言在线运行沙箱技术方案

> 适用项目：knowflow 知识库 / 编程学习平台
> 需求基线：PRD 第 6 章「场景一·编程学习」SC1-IDE-01 / SC1-IDE-02 / SC1-AI-01
> 文档性质：可落地的工程实现方案（当前已实现地基版，并给出生产增强路线）

---

## 1. 概述

### 1.1 目标

为编程学习场景提供「浏览器即 IDE」的沉浸式代码实践能力：用户在网页编辑器编写代码，无需本地安装任何语言运行时，后端在受控环境中**真实编译并运行** Python / Java / JavaScript / C++ 代码，即时返回标准输出、错误信息和耗时，并支持多文件实验工作区与 AI 编程助手内联协助。

### 1.2 范围与非目标

| 范围（本方案覆盖） | 非目标（当前不实现 / 标注为增强路线） |
|---|---|
| 多语言真实执行（解释型 + 编译型） | 在线调试器（断点/变量监视） |
| 单文件即时运行 | 拖拽式 GUI 构建 |
| 多文件持久工作区（可重置沙箱） | 分布式编译集群 |
| 超时强杀 / 输出截断 / 并发限流 | 网络级隔离（依赖 Docker/Judge0 增强） |
| AI 助手内联解释错误 / 问答 | 静态代码分析 + 自动化能力评估（SC1-AI-02） |

### 1.3 支持语言矩阵

| 语言 | 类别 | 执行模型 | 入口约定 |
|---|---|---|---|
| Python | 解释型 | `python3 source.py` | `main.py` / 任意 |
| JavaScript | 解释型 | `node source.js` | `index.js` / 任意 |
| Java | 编译型 | `javac` → `java -cp` | `public class` 类名或文件名 `Main.java` |
| C++ | 编译型 | `g++ -O2` → `./solution.bin` | `main.cpp` / 任意 |

### 1.4 当前实现状态（可落地性验证）

- 后端新增 5 类组件：`CodeExecutionService`(+impl)、`CodeWorkspaceService`(+impl)、`CodeRunController`、`CodeWorkspaceController`、配套 DTO。
- 前端：`CodePlayground.vue` + `api/codeRun.ts` + `api/codeWorkspace.ts`。
- 真实请求验证：四种语言运行、stdin、编译错误、运行时错误、死循环超时强杀、工作区多文件 import、AI 助手错误解释均通过。

## 2. 核心架构设计

### 2.1 整体架构

```
│  └────────┬─────────┘                  │                    │

│  │ CodeExecutionService│  │ CodeWorkspaceService          │ │
│  │ (ProcessBuilder 引擎)│  │ (用户隔离持久目录 + 路径防护) │ │
│  └─────────┬──────────┘   └──────────────┬───────────────┘ │
│            │ 调起                         │ 文件读写         │
│            ▼                             ▼                   │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ OS 运行时: python3 / node / java,javac / g++          │  │

│  └──────────────────────────────────────────────────────┘  │

```

架构遵循「**控制器只做鉴权与编排、执行引擎只做进程管理、工作区服务只做文件隔离**」的分层原则，三者在 `CodeRunController.run()` 中通过 `SecurityUtils.getCurrentUserId()` 取得用户身份后协作，职责单一、可独立替换。

### 2.2 前端代码编辑器

**文件**：`frontend/src/views/CodePlayground.vue`

核心职责：

1. **多语言状态机**：`selectedLanguage` 驱动模板/运行路由；语言下拉含 `python / java / javascript / cpp`（外加 SQL 走前端模拟，不参与沙箱）。
2. **单文件 / 沙箱双模式**：
   - 单文件模式：编辑器内容即提交内容，运行前无需落盘。
   - 沙箱模式（`sandboxMode` 开关）：左侧出现工作区文件面板，编辑器内容先通过 `codeWorkspaceApi.save()` 落盘，再提交 `workspace: true, entryFile: xxx` 到后端按持久目录运行。
3. **运行分发**（`runCode`）：
   ```ts
   if (['python', 'java', 'javascript', 'cpp'].includes(lang)) {
     // 真实沙箱：后端基于系统运行时执行
     const res = await codeRunApi.run({ language: lang, code: userCode.value, workspace, entryFile })
   } else if (lang === 'sql') {
     // SQL 仍走前端 sqlSimulator（练习性质，非沙箱）
   } else {
     // TypeScript 等：浏览器端 JS 直执行
   }
   ```
4. **结果呈现**：控制台三 Tab（输出 / 测试结果 / AI 助手），运行状态标签映射 `CodeRunStatus`：
   - `SUCCESS` → 绿色「运行成功」
   - `COMPILE_ERROR` / `RUNTIME_ERROR` / `TIMEOUT` / `INTERNAL_ERROR` → 相应语义色 + 错误区 + 「AI 解释」快捷按钮。

### 2.3 后端沙箱执行环境

**文件**：`backend/.../service/impl/CodeExecutionServiceImpl.java`

执行引擎基于 JDK 标准库 `ProcessBuilder` 调起系统语言运行时进程，关键设计：

- **进程直执行（Process-based execution）**：每个请求在 OS 级 fork 一个独立子进程运行用户代码，与 Web 服务进程解耦——子进程崩溃/死循环不影响主服务。
- **编译与运行分离**：编译型语言（Java/C++）先执行编译命令、判定编译结果，再决定是否进入运行阶段。
- **无外部中间件依赖**：不依赖 Docker/Judge0 即可运行，降低本地与内网部署门槛（生产增强路线见第 8 节）。

### 2.4 通信机制

| 项 | 说明 |
|---|---|
| 协议 | HTTPS（本地 dev 走 Vite 代理 `/api` → `:8080`） |
| 鉴权 | JWT Bearer，由 `SecurityConfig` 对所有 `/api/code/**` 默认拦截 |
| 请求 | `POST /api/code/run`，JSON Body：`CodeRunRequest` |
| 响应 | `Result<CodeRunResult>`，统一包装 |
| 实时性 | 当前为**同步阻塞 + 超时强杀**（请求线程等待进程结束或超时）；后续可升级为 SSE/WebSocket 流式输出（见 8.3） |
| AI 接口 | `POST /api/code/ai-assist`，JSON Body：`CodeAssistRequest` → `Result<CodeAssistResult>` |

**请求契约示例（Python + stdin）**：
```json
POST /api/code/run
{
  "language": "python",
  "code": "import sys\nprint('you said:', sys.stdin.read().strip())",
  "stdin": "hello",
  "timeLimitMs": 5000
}
```

**响应契约**：
```json
{
  "code": 200,
  "data": {
    "status": "SUCCESS",
    "output": "you said: hello\n",
    "error": null,
    "exitCode": 0,
    "timeUsedMs": 126
  }
}
```

## 3. 安全隔离方案

地基版采用「**进程级 + 目录级 + 权限级**」三层软隔离，足以覆盖受信任内网 / 本地学习环境；生产环境通过第 8 节的 Docker/Judge0 升级获得硬隔离（网络 / 内存 / 进程数）。

### 3.1 容器隔离策略（当前 vs 生产）

| 维度 | 当前实现（地基版） | 生产增强（路线） |
|---|---|---|
| 文件系统 | 每次执行在 `Files.createTempDirectory("knowflow-code-")` 独立临时目录；工作区模式在 `code-workspaces/{userId}/` | 容器只读根文件系统 + 独立 tmpfs 卷 |
| 网络 | 未显式禁用（依赖运行环境无外网） | 容器 `--network=none` 或网络命名空间隔离 |
| 进程 | 独立子进程，超时强杀 | 容器级 cgroup pids 限制 + seccomp 系统调用过滤 |
| 用户 | 与 Web 服务同 OS 用户 | 容器内非 root 用户（如 `runas nobody`） |

**实现要点**：临时目录在 `finally` 中 `deleteRecursively` 清理；工作区目录按 `userId` 物理隔离，跨用户不可见。

### 3.2 资源限制

| 资源 | 限制机制 | 代码落点 |
|---|---|---|
| **CPU / 时间** | 看门狗线程 `process.waitFor(timeLimitMs)` + 超时 `process.destroyForcibly()` 强杀 | `executeCommand()` L285–289 |
| **并发数** | `Semaphore(maxConcurrency)` 限流（默认 8），防止请求洪峰耗尽线程/CPU | `init()` 建信号量，执行前 `acquire()` | 
| **输出大小** | `StreamReader` 按 `outputLimitBytes`（默认 1MB）字节截断，防止巨量输出打爆内存 | `StreamReader.run()` L394–401 |
| **错误/输出展示** | 应用层再截断到 20000 字符并附提示，控制响应体体积 | `truncate()` L330–336 |
| **内存** | 当前 best-effort（macOS 不支持 `ulimit -v`）；生产由容器 `--memory` / cgroup 硬限制 | 见 8.2 |

**超时强杀时序**（底层原理）：
```
T0: ProcessBuilder.start() 启动子进程
T0: 启动 stdout/stderr 两个 StreamReader 后台线程 + 喂入 stdin
T0: process.waitFor(timeLimitMs, MILLISECONDS)
  ├─ 进程正常退出 → 读取 exitValue，进入结果映射
  └─ 超过 timeLimitMs 仍未退出
        → process.destroyForcibly()   // SIGKILL，不可捕获
        → process.waitFor(2000)        // 等僵尸进程回收
        → out.timedOut = true → 状态 TIMEOUT
```

### 3.3 权限控制

1. **接口鉴权**：`/api/code/**` 全部纳入 JWT 校验，`SecurityUtils.getCurrentUserId()` 取当前登录用户；未登录请求被 `SecurityConfig` 拒绝。
2. **工作区路径穿越防护**（`CodeWorkspaceServiceImpl.safeResolve`）：
   - 拒绝绝对路径（`/`、`\` 开头）与 `..` 片段；
   - `dir.resolve(rawPath).normalize()` 后二次校验结果仍 `startsWith(dir)`；
   - 扩展名白名单（`py/js/ts/java/cpp/...`）防止写入可执行/非源码文件。
3. **工作区模式强制登录**：`execute()` 中 `workspace=true` 但 `userId==null` → 直接拒绝（INTERNAL_ERROR 语义）。
4. **最小环境**：`ProcessBuilder` 继承当前进程环境（保证 PATH/JAVA_HOME 可定位运行时），但不注入任何敏感环境变量；临时目录权限受 OS umask 约束。
5. **用户级工作区隔离**：`code-workspaces/{userId}/`，A 用户无法访问 B 用户文件（路径拼接已含 userId，且 `safeResolve` 限制在工作区内）。

## 4. 多语言支持的实现方式

### 4.1 语言抽象层

`Lang` 枚举 + `resolveLang()` 做归一化，支持别名（`py`/`python`、`js`/`javascript`、`cpp`/`c++`）：
```java
private Lang resolveLang(String language) {
    if (language == null) return Lang.UNSUPPORTED;
    return switch (language.trim().toLowerCase()) {
        case "python", "py"   -> Lang.PYTHON;
        case "javascript", "js" -> Lang.JAVASCRIPT;
        case "java"           -> Lang.JAVA;
        case "cpp", "c++", "cplusplus" -> Lang.CPP;
        default               -> Lang.UNSUPPORTED;
    };
}
```
不可识别语言在入口即返回 `INTERNAL_ERROR`，不进入进程执行。

### 4.2 解释型语言（Python / JavaScript）

无需编译，直接以源文件作为参数运行：
```java
List<String> cmd = new ArrayList<>();
cmd.add(bin);                       // python3 或 node
cmd.add(src.getFileName().toString());
ExecOutcome out = executeCommand(cmd, workDir, timeLimit, request.getStdin());
```

**Python 多文件 import 支持**：沙箱模式下 `main.py` 工作目录即工作区根，`import helper` 可解析同目录 `helper.py`（已在验证中确认可用）。

### 4.3 Java（编译 + 运行）

两阶段，且**入口类名自动识别**——支持用户写 `public class Main` 或 `public class Solution`：

```java
// 单文件模式：从源码提取类名命名 .java 文件
String className = javaClassNameFromCode(request.getCode()); // 正则 public\s+class\s+(\w+)
Path src = workDir.resolve(className + ".java");
Files.writeString(src, request.getCode(), UTF_8);

// 编译
List<String> compileCmd = Arrays.asList(javacBin, "-d", workDir.toString(), src.getFileName().toString());
ExecOutcome compile = executeCommand(compileCmd, workDir, Math.max(5000, timeLimit), null);
if (compile.exitCode != 0) { /* COMPILE_ERROR + 取 stderr */ }

// 运行
List<String> runCmd = Arrays.asList(javaBin, "-cp", workDir.toString(), className);
ExecOutcome run = executeCommand(runCmd, workDir, timeLimit, stdin);
```

**工作区模式**：入口类名直接取自文件名（`Main.java` → `Main`），无需正则。

### 4.4 C++（编译 + 运行）

与 Java 同理，编译产物为可执行文件后再运行：
```java
List<String> compileCmd = Arrays.asList(gppBin, "-O2", "-o", bin.toString(), src.toString());
ExecOutcome compile = executeCommand(compileCmd, workDir, Math.max(5000, timeLimit), null);
if (compile.exitCode != 0) { /* COMPILE_ERROR */ }
List<String> runCmd = Arrays.asList(bin.toString());  // 直接执行二进制
```

### 4.5 运行环境管理

- **可执行文件可配置化**：5 个语言运行时路径全部 `@Value` 注入（`code.execution.*-bin`），生产固定为绝对路径，避免 PATH 污染与版本漂移。
- **扩展新语言**：只需在 `Lang` 枚举 + `resolveLang` + `execute()` 的 `switch` 中新增分支，并可选提供编译步骤；接口契约不变。
- **版本一致性**：编译型语言（javac 与 java、g++ 与运行）共享同一 OS 运行时，避免「编译用 JDK 17、运行用 JRE 8」的不一致。

## 5. 沙箱生命周期管理

一次代码执行从请求到资源回收的完整生命周期：

```
[请求] POST /api/code/run
   │
   ▼
① 环境创建
   ├─ 单文件模式: Files.createTempDirectory("knowflow-code-")  ← 临时隔离目录
   └─ 沙箱模式:   workspaceService.getWorkspaceDir(userId)      ← 持久目录(不清理)
   │
   ▼
② 代码执行
   ├─ 写源文件到 workDir（单文件）
   ├─ semaphore.acquire()  ← 并发限流
   ├─ resolveLang → switch 分发到对应 runXxx
   ├─ executeCommand:
   │     ProcessBuilder.start()
   │     喂 stdin → 启动 stdout/stderr StreamReader
   │     waitFor(timeLimit) → 超时 destroyForcibly
   └─ semaphore.release()
   │
   ▼
③ 结果返回
   ├─ applyOutcome(): 映射 ExecOutcome → CodeRunResult
   │     exitCode==0 → SUCCESS
   │     exitCode≠0 → RUNTIME_ERROR(取 stderr)
   │     timedOut   → TIMEOUT
   │     编译 exitCode≠0 → COMPILE_ERROR
   └─ Result<CodeRunResult> 序列化返回前端
   │
   ▼
④ 资源回收
   └─ finally:
        if (workDir != null && !persistent) deleteRecursively(workDir)
        // 临时目录彻底删除；工作区目录保留供下次编辑
```

### 5.1 环境创建

- **临时目录**（单文件）：`Files.createTempDirectory("knowflow-code-")`，JVM 在系统临时区生成唯一目录。
- **持久工作区**（沙箱模式）：`code-workspaces/{userId}/`，首次访问 `Files.createDirectories` 惰性创建；`safeResolve` 保证落在工作区内。

### 5.2 代码执行

见 4.1–4.4。关键不变量：**每个执行请求占 1 个信号量许可 + 1 个独立目录**，互不污染。

### 5.3 结果返回

`ExecOutcome`（内部）→ `CodeRunResult`（对外）映射，状态机如下：

```
                ┌─────────────┐
   exitCode==0  │  SUCCESS    │ (error 仅当 stderr 非空时保留告警)
                └─────────────┘
                ┌─────────────┐
 exitCode≠0 /   │RUNTIME_ERROR│ (pickError 优先 stderr, 兜底 stdout)
 运行阶段异常   └─────────────┘
                ┌─────────────┐
 javac/g++ 失败 │COMPILE_ERROR│ (取编译 stderr)
                └─────────────┘
                ┌─────────────┐
  超过 timeLimit│  TIMEOUT    │ (exitCode=-1, destroyForcibly)
                └─────────────┘
                ┌─────────────┐
 不支持语言/空  │INTERNAL_    │ (入口预校验, 不进进程)
 代码/未登录    │ERROR        │
                └─────────────┘
```

### 5.4 资源回收

- **临时目录**：`finally` 中 `deleteRecursively` 用 `Files.walk` 逆序删除（先子后父），异常仅告警不抛，避免目录泄漏。
- **进程残留**：超时分支 `destroyForcibly()` + `waitFor(2000)` 双保险回收僵尸进程。
- **工作区目录**：执行后保留（用户显式「重置」才清空），符合「可重置实验沙箱」语义。

## 6. 性能优化策略

| 策略 | 实现 | 收益 |
|---|---|---|
| **并发信号量限流** | `Semaphore(maxConcurrency=8)` | 防止编译型语言（CPU 密集）打满线程池与 CPU |
| **超时兜底** | `waitFor(timeLimit)` 强杀 | 避免死循环 / 阻塞调用永久占用线程与信号量 |
| **输出截断** | `StreamReader` 按字节上限 + 应用层 20000 字符截断 | 防止 `while True: print` 类程序耗尽内存与带宽 |
| **StreamReader 异步化** | 独立线程读 stdout/stderr，主线程仅 `waitFor` | 避免管道缓冲满导致子进程阻塞（经典 deadlock 规避） |
| **临时目录复用模式** | 工作区模式下不反复建删目录 | 减少文件系统 I/O，支持多文件项目反复运行 |
| **stdin 写入即关闭** | 无 stdin 时立即 `close()` 输出流 | 子进程不会因等待输入而挂起 |
| **路径 normalize 一次** | `safeResolve` 集中处理 | 避免重复解析开销与穿越漏洞 |

> **设计权衡**：当前「每请求新建进程」模型实现简单、隔离清晰，适合中小并发学习场景；超高并发（如考试）时进程创建开销成为瓶颈，生产可引入**预热进程池 / 容器池**（见 8.3）。

## 7. 异常处理与错误恢复机制

### 7.1 异常分类与处理

| 异常类型 | 触发条件 | 前端呈现 | 自愈/恢复 |
|---|---|---|---|
| 编译错误 | `javac`/`g++` 退出码≠0 | `COMPILE_ERROR` + 编译器 stderr | 用户改代码重试 |
| 运行时错误 | 进程退出码≠0（除零、未捕获异常、缺模块） | `RUNTIME_ERROR` + 错误信息 | 用户改代码；或点「AI 解释」 |
| 超时 | 超过 `timeLimitMs` | `TIMEOUT` + 强杀提示 | 优化算法 / 减小输入 |
| 不支持语言 | `resolveLang` 返回 UNSUPPORTED | `INTERNAL_ERROR` + 提示支持列表 | 用户改选语言 |
| 空代码 | `code` 为空 | `INTERNAL_ERROR` + 「代码为空」 | 用户编写代码 |
| 工作区缺失文件 | `entryFile` 不存在 | `INTERNAL_ERROR` + 文件名 | 用户新建/保存文件 |
| 服务中断 | 线程 `InterruptedException` | `INTERNAL_ERROR` + 「执行被中断」 | 恢复中断标志，可重试 |
| 内部异常 | IO/未知异常 | `INTERNAL_ERROR` + 异常信息 | 服务端日志，联系运维 |

### 7.2 错误恢复关键代码

```java
private void applyOutcome(ExecOutcome out, long timeLimitMs, CodeRunResult result) {
    result.setTimeUsedMs(out.elapsedMs);
    if (out.timedOut) {
        result.setStatus(TIMEOUT);
        result.setError("执行超时（超过 " + timeLimitMs + "ms），已强制终止");
        result.setExitCode(-1);
        return;
    }
    result.setExitCode(out.exitCode);
    result.setOutput(truncate(out.stdout));
    if (out.exitCode == 0) {
        result.setStatus(SUCCESS);
        result.setError(out.stderr.isEmpty() ? null : out.stderr);
    } else {
        result.setStatus(RUNTIME_ERROR);
        result.setError(pickError(out));   // 优先 stderr，兜底 stdout
    }
}
```

### 7.3 AI 助手内联错误恢复（SC1-AI-01）

运行出错时，前端将 `code + error + output` 上下文 POST 至 `/api/code/ai-assist`，后端 `CodeRunController` 经 `AiService.complete` 调大模型生成解释与修正建议。**优雅降级**：未配置/无效密钥时捕获 `BusinessException`，返回 `configured=false` 而非 500，前端展示引导文案——保证「没有 AI 也能跑代码」。

### 7.4 不变量与防御

- `semaphore.acquire()/release()` 置于 `try/finally`，确保异常路径也释放许可。
- 临时目录清理置于最外层 `finally`，与信号量释放解耦，互不遗漏。
- `StreamReader.join(3000)` 避免主线程因读取线程未结束而挂起。
- 所有用户可控路径经 `safeResolve` 校验，杜绝路径穿越导致的越权文件访问。

### 8.2 生产增强清单（按优先级）

| 优先级 | 增强项 | 方案 |
|---|---|---|
| P0 | 网络隔离 | 容器 `--network=none`；或升级 Judge0（已内置隔离） |
| P0 | 内存 / 进程数硬限制 | 容器 `--memory` / `--pids-limit`；Linux `ulimit -v -u` |
| P1 | 非 root 用户 | 容器 `USER nobody`；或 `setuid` 降权运行子进程 |
| P1 | 系统调用过滤 | seccomp profile 限制危险 syscall（如 `fork` bomb 防护） |
| P2 | 流式输出 | SSE/WebSocket 实时回传 stdout，提升大输出体验 |
| P2 | 进程/容器池 | 预热 worker 池，降低高并发下进程创建开销 |

### 8.3 与 Judge0 / Docker 的替换契约

执行引擎以 `CodeExecutionService.execute(CodeRunRequest, Long userId)` 为稳定接口。生产环境只需提供一个新的 `CodeExecutionService` 实现（如 `Judge0CodeExecutionServiceImpl`），通过 HTTP 调用 Judge0 或 `docker run --rm --network=none --memory=128m` 运行用户代码，前端与 `CodeRunController` **无需任何改动**——这正是当前接口契约设计的核心价值。
