## 〇、概述

KnowFlow 当前的形态是「Spring Boot 后端 + Vue 3 SPA」的 Web 项目。围绕"是否要把它做成桌面应用"，存在两条路径分叉，对应**两个截然不同的范围**：

| 维度 | 方案 A：整项目桌面化 | 方案 B：学习工作台模块独立桌面化 |
|------|--------------------|------------------------------|
| **范围** | 把整个 KnowFlow（40+ 控制器、Tika、Ollama、代码沙箱、WebSocket 等）打包成桌面应用 | 仅把「学习工作台」一个模块（收集箱 → 康奈尔笔记 → 间隔重复/记忆宫殿 → 费曼故事）独立做成桌面应用 |
| **目标平台** | Windows + macOS + Linux 三平台 | **仅 macOS** |
| **后端约束** | 必须 Java（保留现有 Spring Boot） | 允许用 Node.js 重写 |
| **结论** | **Electron 35 + Spring Boot 侧车 + jlink 裁剪 JRE** | **Tauri 2 + Node.js(TS) + SQLite** |
| **安装包体积** | ~140–160 MB（JVM 是地板价） | ~60 MB |
| **预计工期** | 2–3 周（不含证书采购） | 5–6 周（单人估算） |

> **关键提醒**：两个方案的结论看起来"互相矛盾"——A 选 Electron、B 选 Tauri——这是因为范围和约束不同，**不是其中一个写错了**。详见各自方案章节的论证。两份方案的"框架选型对比"重叠部分统一收敛到本文末尾的"框架选型对比"章节。

## 一、方案 A：整项目 Electron + JVM 侧车方案

> **适用范围**：把整个 KnowFlow 项目打包成跨三平台桌面应用，后端保留 Spring Boot，把 JVM 打进安装包。
> **一句话结论**：**Electron 35 + Spring Boot 侧车（sidecar）+ jlink 裁剪 JRE**，前端窗口直接加载本地 Spring Boot 托管的 SPA。
> **备选**：Tauri 2（仅当"安装包必须 < 150MB"是硬指标，且你愿意接受 Linux WebKitGTK 的渲染差异）。

### A.1 先看清楚现状（本机实测，非估算）

| 项 | 实测值 | 对桌面化的含义 |
|---|---|---|
| 后端 fat jar | **101 MB**（`backend/target/knowflow-backend-1.0.0.jar`） | 体积大头在这里，不在外壳 |
| 前端 dist | **6.5 MB** | 忽略不计 |
| 后端控制器 | **40+ 个** | 重写后端 = 重做整个项目，直接否决 |
| 前端页面 | **69 个 view** | 纯 SPA，无 SSR，迁移成本极低 |
| Java 版本 | 17（Corretto 17.0.14） | jlink 可用 |
| 上传目录 | `~/knowflow/uploads`（`UploadConfigProperties:39`） | **已经是桌面友好的用户目录**，意外的好消息 |

jar 内最大的几个依赖（可瘦身的靶子）：

```
12.9 MB  sqlite-jdbc        ← 内含全平台 native，可按平台裁到 ~1.5MB
 8.0 MB  bcprov-jdk18on     ← PDFBox 加密 PDF 用，桌面版可排除
 5.7 MB  poi-ooxml-lite     ← docx/pptx 解析，保留
 3.9 MB  swagger-ui         ← 桌面版无用，排除
 2.7 MB  pdfbox             ← 保留
 2.4 MB  mysql-connector-j  ← 桌面版不连 MySQL，排除
```

**关键判断**：这个项目的后端不是"可以顺手换掉的 API 层"，而是承载了 Tika 文档解析、本地代码沙箱、Ollama 本地模型、Obsidian 导入、WebSocket 私信的重资产。桌面化的唯一现实路径是**把 JVM 打进安装包**，而不是重写。

### A.2 核心结论

**推荐：Electron + Spring Boot 侧车进程 + jlink 裁剪 JRE，窗口加载 `http://127.0.0.1:<动态端口>`。**

一句话理由：**JRE + jar 约 150MB 是这个项目的地板价，谁也绕不开。Tauri 省下的 95MB 外壳只占总体积的 35%，却要你付出"三套 WebView 渲染不一致 + 学 Rust"的代价——而你的前端偏偏重度依赖 mermaid / html2canvas / jsPDF 这些最吃浏览器差异的库。**

### A.3 推荐架构与关键实现

#### A.3.1 目录结构

```
knowflow/
├── backend/                  # 不动
├── frontend/                 # 几乎不动
└── desktop/                  # 新增
    ├── package.json
    ├── electron-builder.yml
    ├── src/
    │   ├── main.ts           # 主进程：端口分配 + 拉起 Java + 守护
    │   ├── preload.ts        # 暴露最小 API
    │   └── splash.html       # 启动等待页
    └── resources/            # 打包进 asar 外部
        ├── runtime/          # jlink 裁剪的 JRE（按平台）
        └── knowflow.jar      # 后端 fat jar
```

#### A.3.2 主进程核心逻辑（骨架）

```ts
import { app, BrowserWindow } from 'electron';
import { spawn, ChildProcess } from 'node:child_process';
import net from 'node:net';
import path from 'node:path';
import crypto from 'node:crypto';

/** 让内核分配一个空闲端口，避免 8080 被占 */
function findFreePort(): Promise<number> {
  return new Promise((resolve, reject) => {
    const srv = net.createServer();
    srv.once('error', reject);
    srv.listen(0, '127.0.0.1', () => {
      const port = (srv.address() as net.AddressInfo).port;
      srv.close(() => resolve(port));
    });
  });
}

let backend: ChildProcess | null = null;

async function startBackend(port: number, dataDir: string) {
  const javaBin = path.join(process.resourcesPath, 'runtime', 'bin',
    process.platform === 'win32' ? 'java.exe' : 'java');
  const jar = path.join(process.resourcesPath, 'knowflow.jar');

  backend = spawn(javaBin, [
    '-Xms128m', '-Xmx768m',
    '-XX:+UseSerialGC',              // 桌面单用户，SerialGC 启动更快、内存更省
    '-XX:TieredStopAtLevel=1',       // 只做 C1 编译，砍掉 JIT 预热
    '-Dspring.main.lazy-initialization=true',  // 冷启动提速的关键开关
    '-jar', jar,
    `--server.port=${port}`,
    '--server.address=127.0.0.1',    // 安全红线：只绑回环，禁止局域网访问
    '--spring.profiles.active=desktop',
    `--knowflow.data-dir=${dataDir}`,
  ], { stdio: ['ignore', 'pipe', 'pipe'] });

  backend.stdout?.on('data', d => console.log('[java]', d.toString()));
  backend.stderr?.on('data', d => console.error('[java]', d.toString()));
}

/** 轮询健康检查，起来了再开窗口 */
async function waitHealthy(port: number, timeoutMs = 60000) {
  const deadline = Date.now() + timeoutMs;
  while (Date.now() < deadline) {
    try {
      const r = await fetch(`http://127.0.0.1:${port}/api/health`);
      if (r.ok) return true;
    } catch { /* 还没起来 */ }
    await new Promise(r => setTimeout(r, 300));
  }
  throw new Error('后端启动超时');
}

app.whenReady().then(async () => {
  const port = await findFreePort();
  const dataDir = app.getPath('userData');

  const splash = new BrowserWindow({ width: 420, height: 260, frame: false, resizable: false });
  splash.loadFile(path.join(__dirname, 'splash.html'));

  await startBackend(port, dataDir);
  await waitHealthy(port);

  const win = new BrowserWindow({
    width: 1440, height: 900, show: false,
    webPreferences: { preload: path.join(__dirname, 'preload.js'), contextIsolation: true, nodeIntegration: false },
  });
  await win.loadURL(`http://127.0.0.1:${port}`);
  win.show();
  splash.destroy();
});

/** 必须做：退出时杀干净 Java 子进程，否则会残留占端口 */
app.on('before-quit', () => {
  if (!backend) return;
  if (process.platform === 'win32') {
    spawn('taskkill', ['/pid', String(backend.pid), '/f', '/t']);
  } else {
    backend.kill('SIGTERM');
    setTimeout(() => backend?.kill('SIGKILL'), 3000);
  }
});
```

#### A.3.3 与现有前端栈的集成（接近零改动）

推荐架构里有个关键设计：**不用 `file://` 加载前端，而是让 Spring Boot 把 `dist` 当静态资源托管，窗口直接 `loadURL('http://127.0.0.1:port')`。**

这一步消掉了几乎所有迁移工作量：

- vue-router 保持 **history 模式**不用改（`file://` 下必须改 hash 模式）
- `/api`、`/uploads`、`/ws` 全部同源，**CORS 不用配、axios baseURL 不用改**
- WebSocket 直连同源端口，`vite.config.ts:9` 那个 `__WS_BACKEND_PORT__` 的历史包袱可以顺势去掉
- Spring Security 的现有配置继续有效

前端实际改动 ≈ **只需在启动时从 Electron 拿到端口号**（通过 `preload` 暴露或直接由主进程注入 URL）。

### A.4 后端必须改的 6 处（这是真正的工作量）

| # | 问题 | 现状 | 桌面版怎么改 | 优先级 |
|---|---|---|---|---|
| 1 | **数据库不能要求装 MySQL** | `application.yml:44` 默认 h2 内存库，重启数据全丢；`个人本地部署存储选型建议` 推荐 MySQL | 新建 `application-desktop.yml`，用 **H2 文件模式**：`jdbc:h2:file:${knowflow.data-dir}/db/knowflow;MODE=MySQL;AUTO_SERVER=TRUE`，`init-mode: auto` | **P0 阻塞** |
| 2 | **JWT 密钥 fail-fast** | `application.yml:95` `${JWT_SECRET}` 未设置直接启动失败 | 首启动生成随机 32 字节写入 `userData/config/secret.key`，之后读取 | **P0 阻塞** |
| 3 | **端口写死 8080** | `application.yml:2` | 已由 `--server.port` 覆盖，无需改代码，但要确认无处硬编码 8080 | P0 |
| 4 | **必须绑定回环** | 默认监听 `0.0.0.0`，同一 WiFi 下别人能访问你的知识库 | `--server.address=127.0.0.1` | **P0 安全** |
| 5 | **前端资源托管** | 后端目前不托管 SPA | 把 `frontend/dist` 拷进 `src/main/resources/static/`，加一个 SPA fallback（非 `/api`、`/ws`、`/uploads` 的 404 全部 forward 到 `index.html`） | P0 |
| 6 | **数据目录统一** | `UploadConfigProperties:39` 已用 `~/knowflow/uploads`，但 `code-workspaces`、`config/datasource.json` 是相对路径（`application.yml:48/133`），在 macOS 会写进 `.app` 包内导致失败 | 全部改为基于 `knowflow.data-dir` 的绝对路径 | **P0 阻塞** |

补充的 P1：`spring.main.lazy-initialization=true` + `-XX:TieredStopAtLevel=1` 通常能把冷启动从 5 秒压到 2~3 秒；再激进可以上 **Spring AOT / CDS**，但 Tika 反射多，收益不稳，先别碰。

### A.5 体积瘦身清单（预计省 ~25 MB）

```xml
<!-- desktop profile 下排除 -->
<exclusion>swagger-ui</exclusion>              <!-- 3.9 MB -->
<exclusion>mysql-connector-j</exclusion>       <!-- 2.4 MB -->
<exclusion>bcprov-jdk18on</exclusion>          <!-- 8.0 MB，代价：加密 PDF 解析失效 -->
```

sqlite-jdbc 12.9 MB 里绝大部分是全平台 native 库，打包时按目标平台只保留一份 `org/sqlite/native/<OS>/<arch>/`，可省 ~11 MB。

jlink 裁剪 JRE（Spring Boot 非模块化，用 `jdeps` 反查后手动补模块）：

```bash
jlink --add-modules java.base,java.sql,java.naming,java.management,java.instrument,\
java.desktop,java.security.jgss,jdk.crypto.ec,jdk.unsupported,java.net.http \
  --strip-debug --no-header-files --no-man-pages --compress=zip-6 \
  --output desktop/resources/runtime
```

产出约 **45~55 MB**（对比完整 JDK 300MB+）。

### A.6 体积与性能估算

| 组合 | 解压后 | 安装包（压缩后） | 空闲内存 |
|---|---|---|---|
| Electron 原样 | ~268 MB | ~160 MB | 外壳 250MB + JVM 350MB ≈ **600 MB** |
| Electron 瘦身 | ~233 MB | ~140 MB | 同上 |
| Tauri 原样 | ~173 MB | ~105 MB | 外壳 60MB + JVM 350MB ≈ **410 MB** |
| Tauri 瘦身 | ~138 MB | ~85 MB | 同上 |

结论：Tauri 省 **约 35% 体积 / 约 30% 内存**，不是网上说的 10~20 倍。因为 JVM 那 350MB 常驻内存两边都得付。

真正影响体感的是**冷启动**：Spring Boot 带 40+ 控制器 + MyBatis-Plus 扫描，冷启动约 **3~6 秒**，这个数字远大于 Electron 与 Tauri 之间 1 秒的外壳启动差。**优化启动时间的正确靶子是 JVM，不是外壳选型**（见 A.4 节的 lazy-init + TieredStopAtLevel=1）。

### A.7 分阶段落地计划

| 阶段 | 内容 | 预计工作量 | 交付物 |
|---|---|---|---|
| **P0 可行性验证** | 手写 `main.ts`，本机 `spawn` 现有 jar + 健康探测 + 开窗口。用系统 Java，不打包 | 1~2 天 | 本机能双击跑起来 |
| **P1 后端桌面化** | A.4 的 6 处改造 + `application-desktop.yml` + SPA 托管 + splash | 3~5 天 | 数据持久化、端口不冲突、只绑回环 |
| **P2 打包三平台** | jlink 裁剪 + electron-builder（nsis / dmg / AppImage）+ 依赖瘦身 | 3~5 天 | 三个平台的安装包 |
| **P3 原生化体验** | 托盘、原生菜单、`electron-updater` 自动更新、深链接、开机自启 | 3~5 天 | 像个正经桌面软件 |
| **P4 签名分发** | macOS 公证（需 99 美元/年开发者账号）、Windows 代码签名证书 | 1~2 天 + 采购周期 | 用户不再看到"未知来源"警告 |

**合计约 2~3 周**（不含证书采购）。P0 结束就能看到效果，建议先做 P0 再决定要不要继续。

### A.8 必须提前知道的坑

1. **macOS 公证是硬门槛**：不签名的 `.app` 在 macOS 上会被 Gatekeeper 直接拦下，用户要右键打开甚至改系统设置。要正经分发就得买 Apple Developer（99 美元/年）。Windows 代码签名证书约 ¥1500/年，否则 SmartScreen 会报警。
2. **代码沙箱依赖外部运行时**：`CodeRunController` 会调 `python3` / `node` / `javac` / `g++`（`application.yml:126-130`）。桌面用户机器上大概率没有这些。方案：功能降级——检测不到就在 UI 上灰掉对应语言；Java 可以复用内嵌 JRE 里的 `java`（但 jlink 裁剪版**没有 javac**，要么保留 `jdk.compiler` 模块，要么放弃在线编译 Java）。
3. **Ollama 集成反而是加分项**：`OllamaController` 在桌面场景下终于合理了——本地模型 + 本地知识库，这是 Electron 版最值得宣传的卖点。但要处理 Ollama 未安装的引导提示。
4. **OAuth 回调要改**：`application.yml:139-147` 的 GitHub/微信回调写死 `localhost:8080`。桌面端口是动态的，需要改用自定义协议 `knowflow://oauth/callback` + `app.setAsDefaultProtocolClient`，或者干脆在桌面版隐藏第三方登录。
5. **单实例锁**：必须加 `app.requestSingleInstanceLock()`，否则开两个窗口会有两个 Java 进程抢同一个 H2 文件库，直接锁死。
6. **杀不干净的 Java 子进程**：这是 Electron + JVM 组合最常见的线上问题。Windows 上 `child.kill()` 杀不掉进程树，必须 `taskkill /t`；崩溃退出路径也要覆盖。

### A.9 过渡方案：路线 D（jpackage + 系统浏览器）

用 `jpackage` 把 Spring Boot 打成带图标的原生程序，启动后自动打开默认浏览器访问 localhost。**成本约 1 天**，如果你只是想"先能双击运行"，这是最快的过渡方案，可以作为方案 A 的第 0 阶段。缺点是没有独立窗口、没有托盘、没有原生菜单、浏览器一关就懵。

### A.10 什么情况下方案 A 应该改选 Tauri 2

同时满足以下两条以上就换：

- 安装包体积是**硬性商务指标**（比如要求 < 100 MB）
- 你打算**顺带做 iOS / Android**（Tauri 2 支持，Electron 完全不支持）
- 你愿意投入时间处理 Linux WebKitGTK 上 mermaid / html2canvas 的渲染差异，或者**明确放弃 Linux**（只发 Win + macOS 的话，WebView2 和 WKWebView 都还行，Tauri 的风险大幅下降）

如果只发 Windows + macOS，Tauri 是很有竞争力的选项，可以省 35% 体积和 30% 内存。**但只要 Linux 在支持列表里，Electron 更稳。**

### A.11 方案 A 一句话总结

后端 101 MB 的 fat jar 和 55 MB 的 JRE 是躲不掉的地板价，外壳选型只决定了 35% 的体积差。用 **Electron 包一层、让 Spring Boot 自己托管前端、窗口 loadURL 到 127.0.0.1**，前后端代码改动量最小、三平台渲染一致、工具链最成熟——真正的工作量在后端那 6 处桌面化改造，而不是外壳。

## 二、方案 B：学习工作台 Tauri + Node 方案

> **适用范围**：仅把「学习工作台」模块（收集箱 → 康奈尔笔记 → 间隔重复/记忆宫殿 → 费曼故事 四模块闭环）独立开发为 **macOS 专用**桌面应用。
> **约束（用户给定）**：① 只做 Mac；② 后端技术栈不限 Java，可用 Node.js；③ 综合评价可维护性 / 性能 / 开发效率。
> **一句话结论**：**Tauri 2 + Node.js(TypeScript) + SQLite**，前端最大化复用现有 `Workbench.vue` 及 8 个子组件。

### B.1 为什么这次结论和方案 A 不同

方案 A 评估的是「整个项目打包成桌面应用」，结论是 Electron + Spring Boot 侧车 + 裁剪 JRE，理由是把 40+ 控制器、Tika、代码沙箱、Ollama 全部用 Node 重写不现实，JVM 必须随包分发（地板价 ~156MB）。

方案 B 约束变化后，前提不复存在：

1. **只做「学习工作台」一个模块** —— 实测核对了代码边界：
   - 前端：`Workbench.vue` + 8 个独立子组件（`WorkbenchCapture / Notes / Review / Palace / Recall / Story` 等）+ 单文件 `api/workbench.ts`（14 个端点）。
   - 后端：`WorkbenchController` + `WorkbenchService/Impl`（含 SM-2 约 40 行）+ 8 个实体。
   - 数据：8 张 `wb_*` 表，**全部逻辑外键、按 `userId` 隔离**，不依赖 Tika / Ollama / WebSocket / 代码沙箱。
   - 前端零重渲染库（无 echarts / mermaid），WKWebView 兼容性风险极低。
   - → 模块面积极小且自包含，**用 Node 重写后端完全可行，工作量可控**。
2. **后端允许用 Node.js** —— 不再需要把 JVM 打进安装包，方案 A 最大的体积/复杂度障碍消失。
3. **只做 Mac** —— 打包只需出 `.app/.dmg`，无需 Electron 跨三端的成熟度红利，Tauri 在 macOS（WKWebView 原生）上体验最佳。

**结论翻转：推荐 Tauri 2 + Node.js（TypeScript）后端 + SQLite，前端最大化复用现有 Vue 组件。**

### B.2 后端技术方案选型

目标：用 Node.js 重写 `WorkbenchController` 的 14 个端点 + SM-2 + 遗忘曲线 + 记忆宫殿 + 主动回忆逻辑；数据落本地文件库。

#### B.2.1 运行时与框架

| 方案 | 特点 | 对你(Java 背景) | 推荐度 |
|------|------|----------------|--------|
| **NestJS + TS** | 装饰器 + 模块 + DI，**结构几乎 1:1 映射 Spring Boot**（@Controller/@Service/@Module/@Injectable） | **最低认知 friction**，长期可维护性最好 | ⭐ 首选（结构优先） |
| **Fastify + TS** | 极轻、快、无框架包袱，路由即函数 | 需自己定结构，但模块小无所谓 | ⭐ 首选（精益优先） |
| Express + TS | 生态最大但偏旧、性能弱于 Fastify | 中等 | 备选 |
| 复用 Spring Boot | 需打 JVM 进包 → 违背「Node 后端 + 小体积」初衷 | — | **否决** |

> **推荐：NestJS**（你是从 Java/Spring 过来的，NestJS 的 DI 与分层心智模型直接迁移，出 bug 概率最低、最好维护）。若你更想要最小依赖和最快启动，用 **Fastify + 一层薄 service**。下文示例以 Fastify 为主（更短，便于看懂），结构可平滑升级到 NestJS。

#### B.2.2 数据库

| 方案 | 适用 | 说明 |
|------|------|------|
| **SQLite（better-sqlite3, WAL）** ✅ | 单用户桌面 | 零配置、单文件、随 app 落 `~/Library/Application Support/KnowFlow/workbench.db`。同步 API，无异步陷阱。完美契合 |
| PostgreSQL / MySQL | 多用户/服务端 | 桌面分发不能要求用户装数据库，**否决** |
| LowDB / JSON 文件 | 极简 | 并发与查询弱，SM-2 排程查询会卡，**否决** |

#### B.2.3 ORM / 数据访问

| 方案 | 特点 | 推荐度 |
|------|------|--------|
| **Drizzle ORM** ✅ | 纯 TS、类型安全、无原生引擎、SQL 直观（似 MyBatis 手写 SQL） | ⭐ 首选（轻、无 Rust 二进制要随包） |
| Prisma | schema-first 迁移体验好，但带 Rust 引擎二进制，打包多一层 | 备选 |
| 原生 better-sqlite3 | 最直接，但无类型安全 | 小模块可用 |

> **推荐组合（primary）：Node.js + TypeScript + Fastify/NestJS + better-sqlite3 + Drizzle ORM + SQLite(WAL)。**

#### B.2.4 现有逻辑平移工作量（已核实）

- `WorkbenchServiceImpl.gradeReview`（SM-2）：`quality 0–3` → `easeFactor`(存为整数×100) / `repetitions` / `intervalDay` / `nextReviewTime`，约 40 行 → 平移为 `src/review/sm2.ts`，配单元测试锁定行为。
- 遗忘曲线（`forgetting-curve`）：按 `wb_review_log` 按日聚合 → 一条 SQL `GROUP BY date`。
- 记忆宫殿 / 主动回忆 / 费曼故事：纯 CRUD + 文本比对计分，平移直接。
- 8 张表 schema 直接照搬（去掉 `@TableName` 注解、改成 Drizzle 表定义），字段已确认（`userId/captureId/noteId/categoryId/front/back/cardType/easeFactor/...`）。

### B.3 前后端通信方案

#### B.3.1 主通道：同源 HTTP（复用现有前端，近乎零改）

沿用方案 A 验证过的「后端托管 SPA」技巧，但后端换成 Node：

```
Tauri 窗口  ──loadURL──>  http://127.0.0.1:<动态端口>/
        Node 后端同时托管：
          /            → Vue 构建产物 dist（静态）
          /api/*       → REST 接口（与现有 /workbench/* 路径一致）
          /uploads/*   → 收集箱附件（如有）
```

好处（与现有代码零冲突）：
- `api/workbench.ts` 的 `axios` 用**相对 baseURL**（如 `''` 或 `/api`），不用改。
- vue-router 继续用 **history 模式**（后端做了 SPA fallback），不用退化成 hash。
- **无 CORS**（同源）、**无 WebSocket**（本机调用，SM-2/曲线都是请求-响应即可）。
- 14 个端点路径直接对齐现有 `/workbench/*`，前端子组件基本不动。

#### B.3.2 原生能力桥：Tauri `invoke` + 插件

需要系统能力时走 Tauri（不走 HTTP）：
- 文件导入（收集箱拖入本地文件）：`@tauri-apps/plugin-dialog` + `@tauri-apps/plugin-fs`。
- 本地通知（复习提醒）：`@tauri-apps/plugin-notification`。
- 菜单 / 快捷键 / 托盘：`tauri.conf.json` 配置 + Rust 壳少量代码。
- 自动更新：`@tauri-apps/plugin-updater`。

#### B.3.3 端口与绑定安全（P0）

- 后端**只绑定 `127.0.0.1`**（绝不 `0.0.0.0`），避免同 WiFi 他人访问知识库。
- 端口**动态分配**（避免 8080 被占）；Tauri 启动侧车前先探测可用端口，写入环境变量给 Node。
- 单实例锁：Tauri 配置 `singleInstance`，防止开两个 app 抢同一 SQLite 文件导致库锁死。

### B.4 Mac 应用打包与分发方案

| 环节 | 方案 | 说明 |
|------|------|------|
| 构建 | `tauri build` | 输出 `target/release/bundle/macos/KnowFlow.app` + `.dmg` |
| 签名 | Apple Developer ID Application（$99/年） | **必须**，否则 Gatekeeper 直接拦截 |
| 公证 | `xcrun notarytool`（staple 工单） | 首次打开不被「无法验证开发者」拦 |
| 分发 | **GitHub Releases 直链 .dmg**（首选） | 绕开 Mac App Store 沙箱限制（本地 SQLite + 文件访问在 MAS 沙箱里很受限） |
| 自动更新 | `@tauri-apps/plugin-updater` + Releases feed | 用户无感升级 |
| 加分 | Homebrew Cask | 方便开发者群体安装 |
| **不推荐** | Mac App Store | 强制沙箱，本地文件/SQLite/自动更新都受限，v1 先不做 |

> 只做 Mac → CI 只需 macOS runner，`.github/workflows/release.yml` 一条流水线出 `.app/.dmg` 并上传 Releases。比跨三端简单得多。

### B.5 与现有项目模块的数据交互方式

「独立桌面应用」= 运行时**不依赖**线上 Spring Boot 后端；但要做到能从现有 Web 项目迁移数据。

#### B.5.1 本地优先（Local-first）

- 桌面 app 自带 SQLite，所有工作台数据本地读写，离线可用、隐私可控。
- 启动即建库建表（Drizzle `migrate()`），首次运行零配置。

#### B.5.2 与现有 Web 项目的桥梁：可移植 JSON Schema

定义一份**版本化导出格式** `workbench-export.v1.json`（含 8 张表数据 + 分类树 + 用户画像），两端都实现：

- **Web 端（现有 Spring Boot）**：新增 `GET /api/workbench/export` 导出该 JSON（只需在 `WorkbenchController` 加一个只读端点，不动其它模块）。
- **桌面端**：「导入」按钮读取该 JSON，映射到本地 SQLite。
- 字段映射直白：`wb_capture / wb_note / wb_review_card(+log) / wb_palace(+loci) / wb_recall_session / wb_story` ↔ 同名表。

#### B.5.3 可选：双向同步（后期）

若日后要「Web 与桌面数据互通」，以**同一份 JSON Schema 为契约**，桌面端实现一个轻量同步层：调用现有 `/api/workbench/*` 拉取增量、本地改完推回（带 `updatedAt` 冲突合并）。v1 不做，避免把桌面 app 重新耦合回服务端可用性。

#### B.5.4 分类（doc_category）依赖处理

工作台只用分类做「标签/归类下拉」。桌面端建本地 `categories` 表：首次导入时从 Web 导出带上分类树；或允许用户本地自建。不依赖线上 `doc_category` 实时查询。

### B.6 开发周期与关键技术风险评估

#### B.6.2 关键技术风险

### B.7 方案 B 一句话总结

## 三、框架选型对比（Electron vs Tauri，统一视角）

> 本节把方案 A 与方案 B 中关于 Electron / Tauri 的对比内容**合并去重**，避免重复论述。两个方案对框架的取舍差异，本质上来自**范围、平台、后端约束**三个变量的不同，而不是框架本身的优劣反转。

### 3.1 框架基础对比

| 框架 | 内核 | 包体积(实测估算) | 内存占用 | 前端复用 | 学习曲线(对 Java+Vue 背景) | 原生体验(Mac) | 维护性 |
|------|------|----------------|----------|----------|----------------|---------------|--------|
| **Electron** | 内置 Chromium | ~150MB+ | 高 | 直接复用 Vue | 最低（纯 JS） | 中（自绘，非系统原生） | 中（历史包袱重） |
| **Tauri 2** | 系统 WebView（Win=WebView2 / macOS=WKWebView / Linux=WebKitGTK） | ~60MB（15 Tauri + 45 Node 侧车） | 低（约 1/3 Electron） | 直接复用 Vue | Rust 工具链一次性配置，业务代码仍 JS | **最佳**（原生毛玻璃/菜单/通知） | 高（Rust 壳极薄） |
| SwiftUI | 原生 | ~20MB | 最低 | **不可复用**，需重写 | 高（需学 Swift） | 最佳 | 高但和现有代码脱节 |
| NW.js | 内置 Chromium | ~140MB | 高 | 直接复用 Vue | 低 | 中 | 低（社区弱于 Electron） |
| Flutter Desktop | 自绘引擎 | ~50MB | 中 | **不可复用**（Dart） | 高（Dart 改写） | 中 | 中 |

**关键判断：**
- SwiftUI / Flutter 要抛弃已写好的 Vue 组件，开发效率与可维护性直接判负，**排除**。
- NW.js 社区与安全弱于 Electron，**排除**。
- **Electron vs Tauri 是真正二选一**：Electron 胜在「零 Rust、纯 JS、你最熟」；Tauri 胜在「Mac 上原生体验最好、体积小一半、内存省 2/3」。

### 3.2 五维度逐条对比（适用于方案 A 整项目场景）

#### 维度 1：跨平台兼容性 —— Electron 明显胜出（整项目场景）

Tauri 用系统 WebView：Windows 是 WebView2（Chromium，最好）、macOS 是 WKWebView（Safari 内核）、Linux 是 WebKitGTK（最落后）。整项目前端恰好踩在雷区上：

| 依赖 | 用途 | 在 WebKitGTK 上的风险 |
|---|---|---|
| `mermaid@11` | 知识图谱 / 流程图 | SVG `foreignObject` 文本测量差异，图形错位 |
| `html2canvas@1.4` | 学习报告截图 | 对 CSS 支持度极敏感，跨引擎结果明显不同 |
| `jspdf@4` | 导出 PDF | 依赖 canvas 渲染结果，跟着 html2canvas 一起偏 |
| `tailwindcss@3` | 全站样式 | `backdrop-filter`、`:has()` 在 WebKitGTK 上支持不全 |

Electron 自带同一个 Chromium，三平台**像素级一致**，你只需要测一遍。Tauri 需要三平台各测一遍，且 Linux 上大概率要写降级样式。

> **注意**：此风险**不适用方案 B**——学习工作台模块**未用** echarts/mermaid，纯 CSS/SVG，WKWebView 兼容性风险极低（见 B.6.2 R3）。

#### 维度 2：开发效率 —— Electron 明显胜出（整项目场景）

- 技术背景是 **Java + Vue**，Rust 是第三门语言。Tauri 的侧车配置、权限 capability、打包脚本都要读 Rust 侧文档。
- 更关键的是：方案 A 里 Node 侧要做的事（分配空闲端口、`spawn` Java 进程、健康探测、进程守护、崩溃重启、退出时清理子进程）在 Node 里是十几行，在 Rust 里要处理 `std::process` + 跨平台进程树 kill，坑更深。
- `electron-builder` 的三平台产物、自动更新、签名/公证是成熟流水线；Tauri 2 的 updater 虽已 first-class，但 sidecar + 外置资源的签名组合案例明显更少。

> **注意**：此劣势**在方案 B 中大幅弱化**——只做 Mac，Rust 只用于「启动 Node 侧车 + 窗口管理」约 50 行样板，真正的业务逻辑全在前端 Vue 和后端 Node（都是 JS/TS）。一次性装好 Rust 工具链后，日常开发几乎不碰 Rust。

#### 维度 3：与现有前端栈的集成难度 —— 两者都低

两个方案都采用「后端托管 SPA + 窗口 loadURL 到 127.0.0.1」的架构，前端改动量都接近于零（见 A.3.3 与 B.3.1）。差异只在后端语言（Java vs Node）。

#### 维度 4：性能与包体积 —— Tauri 略胜，但差距是否被 JVM 抹平取决于方案

- **方案 A（整项目，JVM 必须随包）**：JVM 那 350MB 常驻内存两边都得付，Tauri 只省约 35% 体积 / 30% 内存。冷启动 Spring Boot 约 3~6 秒，远大于外壳 1 秒的启动差，**优化靶子是 JVM 不是外壳**。
- **方案 B（工作台模块，Node 后端）**：没有 JVM 包袱，Tauri 体积优势完整兑现——~60MB vs Electron ~150MB+，内存省 2/3。

#### 维度 5：社区与维护活跃度 —— Electron 胜出（且有直接同类先例）

- **Obsidian 就是 Electron 写的**，和 KnowFlow 是同一品类（本地知识库 + Markdown + 插件）。它证明了"Electron 做本地知识工具"这条路完全走得通，遇到的坑网上都有人踩过。
- VS Code / Slack / Discord / Figma / 1Password 仍在 Electron 上，工具链（electron-builder、electron-updater、差量更新、公证）最成熟。
- Tauri 2 已稳定（2.11 线），生态增长快，但"Tauri + JVM sidecar"这个具体组合的中文资料和踩坑帖非常少。
- **方案 B 场景下**：Tauri 在 macOS（WKWebView 原生）上体验最佳，且只发一个平台，工具链成熟度不足的问题不存在。

### 3.3 五条路线总体评分（适用于方案 A 整项目场景）

| 路线 | 跨平台 | 开发效率 | 集成难度 | 体积/性能 | 社区 | 结论 |
|---|---|---|---|---|---|---|
| **A. Electron + SpringBoot 侧车** | ★★★★★ | ★★★★★ | ★★★★★ | ★★★☆☆ | ★★★★★ | **方案 A 推荐** |
| B. Tauri 2 + SpringBoot 侧车 | ★★★☆☆ | ★★★☆☆ | ★★★★☆ | ★★★★☆ | ★★★☆☆ | 体积硬指标时选它 |
| C. jpackage + JavaFX WebView | ★★★☆☆ | ★★★☆☆ | ★★☆☆☆ | ★★★★☆ | ★★☆☆☆ | 否决：WebView 内核老，mermaid 大概率挂 |
| D. jpackage + 调起系统浏览器 | ★★★★☆ | ★★★★★ | ★★★★★ | ★★★★★ | ★★★☆☆ | 1 天就能做，但**不是真桌面应用**（见 A.9） |
| E. 后端重写为 Node/Rust | ★★★★★ | ☆☆☆☆☆ | ☆☆☆☆☆ | ★★★★★ | ★★★★☆ | 方案 A 否决：40+ 控制器等于重做项目；方案 B 正是此路线但范围可控 |

> 路线 E 在方案 A 中被否决（重写 40+ 控制器不现实），但在方案 B 中正是采纳的路线——因为工作台模块只有 14 个端点、8 张表，重写工作量可控。

## 四、推荐结论

### 4.1 两个方案不是二选一，而是按需求分叉

| 你的需求 | 推荐方案 | 推荐框架 | 推荐后端 |
|---------|---------|---------|---------|
| **要把整个 KnowFlow 做成跨三平台桌面应用**（保留 Tika/Ollama/代码沙箱等全部能力） | 方案 A | **Electron 35** | Spring Boot 侧车 + jlink 裁剪 JRE |
| **只要把「学习工作台」模块独立做成 Mac 应用**（离线可用、本地优先） | 方案 B | **Tauri 2** | Node.js + TypeScript + SQLite |

### 4.2 方案 A 推荐结论

后端 101 MB 的 fat jar 和 55 MB 的 JRE 是躲不掉的地板价，外壳选型只决定了 35% 的体积差。用 **Electron 包一层、让 Spring Boot 自己托管前端、窗口 loadURL 到 127.0.0.1**，前后端代码改动量最小、三平台渲染一致、工具链最成熟——真正的工作量在后端那 6 处桌面化改造，而不是外壳。

**改选 Tauri 的触发条件**（满足两条以上）：安装包体积是硬性商务指标（< 100 MB）/ 打算顺带做 iOS/Android / 明确放弃 Linux 只发 Win+macOS。

### 4.3 方案 B 推荐结论

用 **Tauri 2 做 Mac 外壳、Node.js(TypeScript, Fastify/NestJS) 做后端、SQLite 落本地数据**，最大化复用现有 `Workbench.vue` 及 8 个子组件；通信走同源 HTTP（后端托管 SPA），原生能力走 Tauri invoke；数据本地优先 + 一份版本化 JSON 实现与现有 Web 项目单向迁移。预计 5–6 周可交付一个 ~60MB、原生体验、离线可用的 Mac 应用。

**务实备选**：若明确不想装 Rust/Xcode CLT 工具链，方案 B 也可改用 Electron，代价是包大 ~90MB、内存高一些，但不影响功能，P0 约省 1–2 天。

### 4.4 两方案共通的注意事项

无论选哪个方案，以下事项都必须处理：

1. **只绑定 `127.0.0.1`**：绝不监听 `0.0.0.0`，避免同 WiFi 他人访问本地知识库（A.4 #4 / B.3.3）。
2. **端口动态分配**：避免 8080 被占，启动前探测空闲端口（A.3.2 `findFreePort` / B.3.3）。
3. **单实例锁**：防止开两个 app 抢同一个本地数据库文件导致锁死（A.8 #5 / B.3.3）。
4. **子进程清理**：退出时必须杀干净后端子进程，Windows 用 `taskkill /t`（A.3.2 / A.8 #6）。
5. **macOS 公证**：不签名不分发的 `.app` 会被 Gatekeeper 拦截，需 Apple Developer 账号（$99/年）+ `notarytool` 公证（A.8 #1 / B.4）。
6. **后端托管 SPA**：两个方案都用「后端把前端 dist 当静态资源托管 + SPA fallback」的架构，让前端改动量趋近于零（A.3.3 / B.3.1）。
