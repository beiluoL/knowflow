### 三个必须正视的结构性短板

1. **向量检索是"全表扫描 + Java 内存算余弦"** —— 没有任何向量索引，也没有向量数据库。
2. **搜索只有 `LIKE '%kw%'`** —— 仅匹配 title/summary/tags 三个字段，无全文索引、无语义入口。
3. **标签是 `VARCHAR(500)` 逗号分隔字符串** —— 无独立标签表，导致标签无法统计、无法聚合、无法自动生成。

## 一、功能扩展维度

### 1.1 内容管理

#### ① 版本控制 —— 当前 **零实现**

全库扫描 `version_no` / `revision` / `history` 关键词命中 0，`doc_document` 表无任何版本字段。团队协作场景下"改错了回滚不了"是硬伤。

**方案**：新增 `doc_document_version` 表，走"快照 + 差异展示"路线（不做 Git 式增量，复杂度不划算）。

```sql
CREATE TABLE IF NOT EXISTS doc_document_version (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    doc_id BIGINT NOT NULL COMMENT '文档ID（逻辑外键 doc_document.id）',
    version_no INT NOT NULL COMMENT '版本号，从 1 递增',
    title VARCHAR(200),
    content MEDIUMTEXT COMMENT '该版本正文快照',
    summary VARCHAR(500),
    change_log VARCHAR(500) COMMENT '变更说明',
    editor_id BIGINT COMMENT '编辑人（逻辑外键 sys_user.id）',
    char_delta INT COMMENT '相对上版本字符增减',
    create_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    update_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    deleted INT DEFAULT 0
);
CREATE UNIQUE INDEX uk_doc_version ON doc_document_version(doc_id, version_no);
CREATE INDEX idx_dv_editor ON doc_document_version(editor_id);
```

实现要点：
- 在 `DocServiceImpl.update()` 里前置一次快照写入，事务内完成；
- 前端用 `diff-match-patch`（体积 ~20KB）做左右分栏差异高亮，不必引入重型编辑器；
- 保留策略：默认留最近 20 版 + 每个自然月首版，避免 `MEDIUMTEXT` 无限膨胀；
- 回滚 = 把旧版内容写成新版（永不物理删除），符合项目既有的逻辑删除约定。

#### ② 内容审核机制 —— 当前 **零实现**

`audit_status` / `review_status` 全库命中 0。`doc_document.status` 只有 0/1 两态，语义是"上下架"而非"审核"。社区帖同样直接发布即可见。

**方案**：引入统一审核流，不为文档单独造轮子。

```sql
ALTER TABLE doc_document ADD COLUMN audit_status INT DEFAULT 1
    COMMENT '审核状态：0待审/1通过/2驳回/3AI疑似违规';
ALTER TABLE doc_document ADD COLUMN audit_remark VARCHAR(500);
ALTER TABLE community_post ADD COLUMN audit_status INT DEFAULT 1;
CREATE INDEX idx_doc_audit ON doc_document(audit_status);
```

- **一审用 AI**：复用已有 `AiService.complete()`，提交时异步跑一次合规打分（涉政/涉黄/广告/抄袭嫌疑），高风险打 `audit_status=3` 进人工队列，低风险直接放行 —— 这样 95% 内容不增加人工成本；
- **二审用人**：`AdminDocController` 加 `/audit` 端点，前端 `admin/CommunityManage.vue` 已有壳可扩展成统一审核台；
- 审核开关做成配置项，个人版可全关，企业版打开。

#### ③ 批量操作

现有管理端是逐条操作。建议在 `admin/DocManagement.vue` 加多选 + 批量移动分类 / 批量打标签 / 批量导出 / 批量重新索引。后端提供 `POST /api/admin/docs/batch`，用 MyBatis Plus `updateBatchById` 单事务处理，注意**限制单批 ≤ 200 条**防长事务锁表。

#### ④ 更多导入格式

Tika 已覆盖主流格式，真正缺的是**结构化导入源**：
- **Markdown 文件夹/ZIP 批量导入**（保留目录层级 → 自动建分类树），成本低价值高，优先做；
- **网页 URL 抓取**（Jsoup + Readability 算法提正文）；
- **Notion / 语雀 / 飞书 导出包解析**；
- **图片 OCR**：Tika 配合 Tesseract 可解析扫描件，需额外装 `tesseract-ocr` 二进制。

### 1.2 智能检索增强

#### 现状问题（这是全项目投入产出比最高的改进区）

```java
// DocServiceImpl.java:90-92 —— 全部检索能力就这三行
w.like(DocDocument::getTitle, dto.getKeyword())
 .or().like(DocDocument::getSummary, dto.getKeyword())
 .or().like(DocDocument::getTags, dto.getKeyword());
```

`LIKE '%kw%'` 前置通配符**必然全表扫描**，且正文 `content` 根本不参与检索 —— 用户搜一个只在正文里出现的词，一条都搜不到。

#### 方案（三步走）

**第一步：中文全文索引（1 天，立竿见影）**

MySQL 8 用 ngram 解析器建全文索引：

```sql
ALTER TABLE doc_document
  ADD FULLTEXT INDEX ft_doc_content (title, summary, content) WITH PARSER ngram;
-- my.cnf: ngram_token_size=2
```

查询改 `MATCH ... AGAINST (? IN BOOLEAN MODE)`，附带 relevance 打分。注意 H2 不支持 ngram，需在 Mapper 层做数据库方言分支，或本地开发仍走 LIKE。

**第二步：混合检索 + RRF 融合（3 天，质量跃升）**

单纯向量检索对专有名词、代码符号、精确匹配很弱；单纯 BM25 对语义改写很弱。工业界标准做法是两路召回后用 RRF（Reciprocal Rank Fusion）融合：

```java
// 伪代码：score = Σ 1/(k + rank_i)，k 取 60
Map<Long, Double> fused = new HashMap<>();
for (int i = 0; i < bm25Results.size(); i++)
    fused.merge(bm25Results.get(i).getId(), 1.0 / (60 + i + 1), Double::sum);
for (int i = 0; i < vectorResults.size(); i++)
    fused.merge(vectorResults.get(i).getId(), 1.0 / (60 + i + 1), Double::sum);
```

**第三步：高级筛选 + 个性化（2 天）**

- 筛选面：分类 / 标签 / 难度 / 时间范围 / 作者 / 文档类型 / 是否已读 —— 字段都已存在，只是没暴露；
- 个性化：新增 `search_history` 表记录查询词与点击文档，用"用户高频分类 + 已收藏标签"对结果做加权重排（简单加权即可，不必上机器学习）；
- 搜索建议：基于历史词 + 标签词做前缀补全。

#### 多模态搜索

问答已支持图片输入（`ChatServiceImpl.java:86-94`），但**搜索入口不支持**。建议：以图搜图用 CLIP 类模型出图像向量存 `doc_chunk`（加 `chunk_type` 区分 text/image）；优先级不高，除非业务确有图片资料库场景。

### 1.3 知识图谱完善

这块基础比预想好 —— AI 实体关系抽取已落地（`KnowledgeService.extractDoc()`），实体按名称合并、关系四元组去重都做了。真正的缺口在**质量与规模**：

| 问题 | 现状证据 | 改进方案 |
|---|---|---|
| 实体合并太粗糙 | `upsertEntity()` 按 `name` 精确匹配 | "Spring Boot"/"SpringBoot"/"springboot" 会建成 3 个实体。加**归一化层**：小写化 + 去空格符号 + 别名表 `kg_entity_alias`，再辅以 embedding 相似度 >0.92 判同义 |
| 批量抽取无并发无进度 | `extractByCategory()` 串行 for 循环，上限 200 篇 | 200 篇 × 每篇一次 LLM 调用 ≈ 十几分钟阻塞。改**异步任务 + 进度轮询**（`@Async` + 任务表），前端显示进度条 |
| 无知识推理 | 只存直接关系 | 加**二跳推理**：A 依赖 B、B 依赖 C ⇒ 提示 A 间接依赖 C；用递归 CTE 或 Java 侧 BFS（深度限 3）实现，无需图数据库 |
| 自动标签未打通 | `tags` 是逗号字符串，抽取出的实体没回写标签 | 抽取完成后把高权重实体**自动回写为文档标签**，一举解决"自动打标"需求 |
| 可视化性能 | 分类图谱一次性全量返回所有分类+文档节点 | 文档量上千后浏览器卡死。加**分层加载**（先分类层，点击展开文档层）+ 节点数上限 + Canvas 渲染替代 SVG |

**标签体系重构**（这是连锁改造的关键节点）：

```sql
CREATE TABLE IF NOT EXISTS doc_tag (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    ref_count INT DEFAULT 0 COMMENT '引用次数，用于热门标签',
    source INT DEFAULT 0 COMMENT '0手动/1AI生成',
    create_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    update_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    deleted INT DEFAULT 0
);
CREATE UNIQUE INDEX uk_tag_name ON doc_tag(name);

CREATE TABLE IF NOT EXISTS doc_tag_rel (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    doc_id BIGINT NOT NULL,
    tag_id BIGINT NOT NULL,
    create_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    update_time TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    deleted INT DEFAULT 0
);
CREATE UNIQUE INDEX uk_doc_tag ON doc_tag_rel(doc_id, tag_id);
CREATE INDEX idx_tagrel_tag ON doc_tag_rel(tag_id);
```

迁移时保留 `doc_document.tags` 冗余字段做列表展示（避免 N+1），双写过渡。

## 二、技术优化维度

### 2.1 RAG 性能优化（**最高优先级技术债**）

#### 问题诊断

```java
// DocChunkServiceImpl.java:97-119
List<DocChunk> allChunks = docChunkMapper.selectList(...);  // ① 全表加载
return allChunks.parallelStream()
    .map(chunk -> { parseVector(chunk.getEmbedding()); ... })  // ② 逐条字符串解析
    .sorted(...).limit(size)                                    // ③ 全量排序
```

三个致命点：

1. **全表加载**：每次提问把**所有** chunk 连同 embedding 文本一起读进内存。1536 维向量存成逗号分隔字符串约 **18KB/条**。1 万个 chunk = **180MB 单次查询**，直接 OOM 风险。
2. **重复解析**：每次检索都要把 18KB 字符串 `split(",")` + `Float.parseFloat()` 解析 1536 次 —— 1 万 chunk 就是 1536 万次解析，纯 CPU 浪费。
3. **索引串行**：`indexDocument()` 第 60-74 行 for 循环里**逐块同步调 embedding API**。一篇 100 块的文档 = 100 次串行 HTTP，按 200ms/次算要 20 秒，且是在上传请求线程里同步跑。

#### 分阶段方案

**阶段一：零新依赖优化（1-2 天，性能提升 10-20 倍）**

```java
// 1. embedding 改二进制存储：TEXT(18KB) → BLOB(6KB)，省 66% 空间，解析快 50 倍
ByteBuffer buf = ByteBuffer.allocate(vec.size() * 4);
vec.forEach(buf::putFloat);
chunk.setEmbeddingBlob(buf.array());

// 2. 内存缓存向量（Caffeine，项目已有 hutool 也可先用 ConcurrentHashMap）
@Cacheable("chunkVectors")
public float[][] loadAllVectors() { ... }   // 启动/变更时加载，检索零 IO

// 3. 批量 embedding：OpenAI 接口原生支持 input 数组，100 次调用 → 1 次
Map.of("model", model, "input", chunkTextList)

// 4. 索引异步化：@Async 后台索引，上传立即返回
```

**阶段二：向量数据库选型（3-5 天）**

| 方案 | 优势 | 劣势 | 适配度 |
|---|---|---|---|
| **Elasticsearch 8** | kNN + BM25 一站解决，**同时干掉全文检索缺口**，Java 生态成熟 | 内存占用大（≥2G），运维重 | ⭐⭐⭐⭐⭐ 一石二鸟，**推荐** |
| **Qdrant** | 单机 Docker 极简，Rust 高性能，payload 过滤强 | 只解决向量，全文检索还得另做 | ⭐⭐⭐⭐ 轻量优选 |
| **pgvector** | 与关系数据同库，事务一致 | 需从 MySQL 迁 PostgreSQL，成本高 | ⭐⭐ 不建议为此换库 |
| **Milvus** | 亿级向量能力 | 对本项目严重过剩，依赖 etcd/MinIO | ⭐ 过度设计 |

**推荐 ES 8**：它同时解决 §1.2 的中文全文检索和本节的向量检索，两个痛点一次投入。用 `spring-boot-starter-data-elasticsearch`，`dense_vector` 字段 + HNSW 索引，检索从 O(n) 降到 O(log n)。若嫌运维重，退而求其次选 Qdrant + MySQL ngram 全文索引组合。

**阶段三：检索质量提升（3-4 天）**

- **分块重叠**：当前切分无 overlap，跨块语义被切断。加 15% overlap（500 字块 → 75 字重叠）；
- **语义分块**：优先按 Markdown 标题层级切，退化再按段落，保留 `heading_path` 作为 chunk 元数据；
- **查询改写**：用小模型把口语化提问改写成检索友好查询（"这玩意咋配"→"配置方法"），或用 HyDE（先让 LLM 生成假想答案再检索）；
- **重排序**：召回 Top-20 后用 `bge-reranker-base` 精排取 Top-5，这是提升相关性最有效的单一手段；
- **引用溯源**：当前 `ChatServiceImpl.java:153-158` 用 chunk 内容伪造 DocDocument 对象，**丢失了 chunk 与原文的位置关联**。应返回 `chunkId + docId + 字符偏移`，前端点击引用直接跳转原文并高亮。

### 2.2 AI 能力增强

| 能力 | 现状 | 方案 |
|---|---|---|
| 智能摘要 | `summary` 字段靠手填 | 上传后异步调 LLM 生成 200 字摘要 + 3-5 个关键点，写回 `summary`。复用 `AiService`，一次调用搞定 |
| 自动标签 | 无 | 与 §1.3 图谱实体抽取**合并成一次 LLM 调用**（同时输出实体、关系、标签、摘要），省 3 倍 token |
| 内容质量评估 | 无 | 多维打分（完整性/准确性/可读性/时效性），存 `doc_document.quality_score`，用于搜索排序加权与"待改进文档"看板 |
| 多语言 | 无 | i18n 是前端工程问题（vue-i18n）；**内容多语言**更实际：检索时用多语言 embedding 模型（`bge-m3`），实现中文提问检索英文资料 |
| 成本控制 | 无任何统计 | 加 `ai_call_log` 表记录 token 消耗与耗时，管理端出成本看板；对 embedding 做**内容 hash 去重缓存**（同文本不重复调用），实测可省 30%+ |

### 2.3 数据存储优化

- **`content` 字段类型**：当前 `TEXT`（上限 64KB），而 Tika 抽取上限是 50 万字符（约 1.5MB UTF-8）——**长文档会被静默截断**。应改 `MEDIUMTEXT`（16MB）。这是一个当前就存在的潜在数据丢失风险。
- **冷热分离**：`doc_chunk.content` 与正文重复存储，1 万文档量级后 embedding 列会成为最大表。建议 chunk 只存偏移量指针（`start_offset`/`end_offset`）而非全文副本，省 50% 空间。
- **文件存储**：当前落本地磁盘（`UploadHelper`），无法水平扩展。抽象 `StorageService` 接口，实现本地 / MinIO / 对象存储三种，生产切对象存储。
- **索引审计**：`doc_chunk` 表目前只有主键，`doc_id` 上应补索引（逻辑外键必须建索引 —— 这是项目已遵循的阿里规约，此表是漏网之鱼）。

## 三、用户体验维度

### 3.1 移动端

- **响应式覆盖率仅 37%**（65 个页面中只有 24 个用了 `sm:`/`md:` 断点）。管理端页面基本没做移动适配。建议先保证 C 端 20 个高频页 100% 覆盖，管理端可放弃移动端。
- **离线访问**：PWA 骨架已有（`vite-plugin-pwa`），但**全库 IndexedDB 命中 0** —— 只缓存了静态资源，文档内容不可离线。方案：用 `idb` 库缓存"我的收藏 + 最近阅读 + 已下载"三类文档正文，配合 workbox `NetworkFirst` 策略。
- **推送通知**：`useStudyReminder.ts` 是本地 Notification 定时器，**关掉浏览器就失效**。要真触达需 Web Push + VAPID 密钥 + 后端推送服务（`web-push` 协议）。代码里已预留 `subscribePush` 接口，补后端即可。
- **扫码录入**：小程序端已有 10 个页面基础，加 `wx.scanCode` + 拍照 OCR 上传是自然延伸。

### 3.2 交互体验

已有基础：拖拽上传（`dragover`/`@drop` 命中 4-5 处）、快捷键（`keydown` 19 处）、分享（9 处）、Mermaid 渲染、番茄钟。建议补：

- **全局命令面板**（Cmd+K）：搜索文档 / 跳转页面 / 执行命令三合一，这是知识库产品的标配，用现有搜索接口即可实现；
- **Markdown 实时预览**：已引入 `markdown-it`，编辑页做左右分栏同步滚动；
- **划词工具条**：选中文本后浮出「高亮 / 批注 / 问 AI / 生成闪卡」—— 把知识库和已有的 AI 问答、闪卡系统串起来，这是本项目最有特色的连接点；
- **阅读进度与目录**：长文档右侧自动生成 TOC + 阅读进度条（`doc_read_progress` 表已存在，前端未充分利用）。

### 3.3 个性化

- **主题切换**：`theme` 关键词命中 12 处但无暗色模式（`dark-mode` 命中 0）。Tailwind 加 `darkMode: 'class'` + CSS 变量，工作量约 1 天，用户感知强；
- **个人知识仪表板**：`LearningReport.vue` 与 `LearningCenter.vue` 存在大量重复代码，建议合并重构为统一仪表板，补齐掌握度分布看板（这是历史遗留缺口）；
- **布局自定义**：仪表板卡片支持拖拽排序 + 显隐配置，存 `sys_user` 的 JSON 偏好字段。

## 四、商业价值维度

### 4.1 企业级功能（当前全部 **零实现**）

扫描确认：`tenant_id` / `order_no` / `payment` / `vip` / `member_level` 关键词全库命中 **0**。

**多租户改造路径**（三选一，按成本递增）：

| 模式 | 实现 | 成本 | 适用 |
|---|---|---|---|
| 共享库 + `tenant_id` 列 | 所有表加 `tenant_id`，用 MyBatis Plus `TenantLineInnerInterceptor` 自动注入过滤 | **低**（插件自动改写 SQL，业务代码几乎不动） | **推荐起步** |
| 独立 Schema | 每租户一套表 | 中 | 数据隔离要求高 |
| 独立实例 | 每租户一套服务 | 高 | 大客户定制 |

MyBatis Plus 的多租户插件是这里最大的红利 —— 加个 `TenantLineHandler` 配置类，44 张表自动带上租户过滤，改造量远低于想象。

**付费会员体系**：需新增 `sys_order`（订单）、`sys_membership`（会员等级与有效期）、`sys_benefit`（权益配置）三表；权益控制用注解 `@RequireMembership(level = "PRO")` + AOP 拦截。可付费点建议锚定 AI 成本项：AI 问答次数、向量索引容量、知识库成员数、导出次数。

**数据分析报表**：`AdminOverviewController` 已有基础统计，缺留存/活跃/漏斗分析。建议加轻量埋点表 `sys_event_log`，按天聚合成 `sys_daily_stat` 避免实时聚合拖垮库。

### 4.2 集成扩展

- **API 开放平台**：项目已有 237 个 REST 端点 + springdoc-openapi，**离开放 API 只差认证层**。加 `sys_api_key` 表 + 一个 `ApiKeyAuthFilter`（与现有 JWT Filter 并列）+ 基于 Bucket4j 的限流，就能对外提供服务。这是投入产出比很高的一项。
- **Webhook**：`sys_webhook` 表（url + secret + 订阅事件），文档创建/更新/审核通过等事件异步 POST，HMAC-SHA256 签名，失败指数退避重试 3 次。
- **OAuth 2.0**：现在是"用 GitHub 登录我"（客户端角色），企业需求往往是"用我的账号登录别的系统"（**服务端角色**）。要做需引入 Spring Authorization Server，工作量较大，建议等有明确客户需求再上。
- **插件系统**：Java 侧热插拔成本高（需 SPI + 独立 ClassLoader），**不建议现阶段做**。更务实的是"自定义 AI 工作流"配置化（用户配置 prompt 模板 + 触发时机），覆盖 80% 的定制诉求。

## 六、三条核心判断

1. **不要急着上向量数据库**。先做 P0-1 的存储与缓存优化 —— 二进制存储 + 内存缓存 + 批量 API 这三招能把当前架构的天花板从千级 chunk 提到十万级，够用很久。等真到瓶颈再上 ES，那时需求也更清晰。

2. **ES 8 比纯向量库更划算**。项目同时缺"中文全文检索"和"向量索引"两块能力，ES 一次引入解决两个问题；单纯上 Qdrant 只解决一半，全文检索还得再想办法。

3. **最有特色的机会是"知识库 × 学习系统"的连接**。项目已经同时拥有文档库、RAG 问答、闪卡、错题本、学习路径、知识图谱 —— 这套组合在同类产品里并不常见。「划词 → 生成闪卡 → 进入 SM-2 复习队列」「文档 → AI 出题 → 错题本 → 薄弱点定位」这类打通，比再补十个通用知识库功能更能形成产品壁垒。建议把 P1 的 #8、#9 与已有学习模块串起来做。
