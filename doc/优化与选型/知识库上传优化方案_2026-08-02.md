## 1. 现状诊断（基于代码实测）

### 1.1 三个上传入口，实现严重不一致

| 入口 | 文件 | 上传方式 | 进度条 |
|---|---|---|---|
| 导入知识库（目录） | `frontend/src/views/KnowledgeImport.vue:534` | 整目录一次 FormData 提交 | ❌ **假的**（CSS 脉冲动画，`:271` + `:1154`） |
| 文档上传 | `views/UploadDoc.vue:363` | 串行逐文件 | ✅ 真实 |
| 知识库上传 | `views/KnowledgeUpload.vue` | 串行逐文件（与上者近乎重复实现） | ✅ 真实 |

### 1.2 具体缺陷清单

**P0 — 目录导入会整批失败**

```js
// KnowledgeImport.vue:548-553
const formData = new FormData()
for (const file of selectedFiles.value) {
  formData.append('files', file, relPath)   // 全部文件塞进同一个请求
}
```

- `spring.servlet.multipart.max-request-size: 500MB`（`application.yml:36`）→ 目录超 500MB 直接 **413，一篇都进不去**
- 无文件数上限、无单文件体积校验、无 `accept` 白名单（`:123-125`）
- 网络抖动 / 超时 → **已传的 99% 全部作废**，从零重来
- `timeout: 300000`（`api/knowledgeImport.ts:16`）→ 大目录必超时，因为后端 Tika 解析是**同步**的

**P0 — 进度条是假的**

```html
<!-- KnowledgeImport.vue:271 -->
<div class="progress-bar-fill" style="width: 100%"></div>
```

用户看到的是一条来回脉冲的动画条，与真实传输字节数**零关联**。10GB 目录和 10KB 文件的视觉表现完全一样。

**P1 — 分片能力完全缺失**

全仓搜索 `chunk|shard|md5|resume|part` 后确认：
- `doc_chunk` 表（`schema.sql:802`）是 **RAG 语义分块**，与上传分片无关
- 无 `/chunk`、`/merge`、`/check` 接口，无分片记录表，无临时分片目录
- 唯一的哈希是 `sha256(正文文本)`（`KnowledgeImportServiceImpl.java:709`），用于**内容增量去重**，不是文件秒传

**P1 — 后端阻塞式处理**

`DocServiceImpl.uploadDoc`（`:168-229`）在同一个请求线程内完成：落盘 → Tika 解析 → 入库 → RAG 分块 `docChunkService.indexDocument`。大文件时请求线程被长期占用，Tomcat 连接池容易被打满。

**P2 — 已知隐患**

- `KnowledgeImportServiceImpl.readContent()`（`:702`）对所有文档按 **UTF-8 纯文本**读取，PDF/DOCX 导入会得到乱码
- `/uploads/**` 静态映射直出，若允许上传 `.html/.svg` 存在存储型 XSS 风险
- 应用层硬编码 `MAX_UPLOAD_BYTES = 50MB`（`DocServiceImpl.java:164`）与 yml 配置双头管理

## 3. 分片上传协议设计

### 3.1 四段式流程

```
① init   → 算 hash，问服务端「传过没 / 传到哪了」
② chunk  → 并发传缺失分片（可暂停、可重试）
③ merge  → 服务端顺序合并 + 整文件校验
④ async  → 解析 / 入库 / RAG 索引异步化，前端轮询或 SSE
```

### 3.2 接口定义

统一前缀 `/api/upload`，均需 JWT（**记得在 `SecurityConfig` 中显式配置，本项目只放行白名单 GET**）。

#### `POST /api/upload/init`

```json
// 请求
{
  "fileHash": "a3f5...(64位 SHA-256)",
  "fileName": "深度学习.pdf",
  "fileSize": 734003200,
  "chunkSize": 5242880,
  "categoryId": 12,
  "relPath": "AI/机器学习/深度学习.pdf"
}
// 响应
{
  "uploadId": "5f2c8a...",
  "instant": false,          // true = 秒传命中，直接跳到完成态
  "docId": null,             // 秒传时返回已建好的文档 id
  "uploadedChunks": [0,1,2,7]  // 断点续传：已存在的分片索引
}
```

**幂等**：同一 `(fileHash, userId)` 重复 init 返回同一个 `uploadId`，这就是断点续传的入口。

#### `POST /api/upload/chunk`

`multipart/form-data`：`uploadId` + `index` + `chunk`(MultipartFile)。
服务端写入 `{uploadDir}/chunks/{fileHash}/{index}.part`，更新任务位图。**先校验 index 范围与 uploadId 归属，防越权写入。**

#### `POST /api/upload/merge`

```json
{ "uploadId": "5f2c8a..." }
→ { "fileUrl": "/uploads/2026/08/02/uuid.pdf", "docId": 3312, "parseStatus": "PARSING" }
```

合并用 `FileChannel.transferTo` 顺序追加（零拷贝），合并完**重算整文件 SHA-256 比对**，不一致则回滚并要求重传。校验通过后删除 `chunks/{fileHash}/` 目录。

#### `GET /api/upload/status?uploadId=xxx` / `DELETE /api/upload/{uploadId}`

分别用于查询进度（含服务端解析阶段）和主动取消 + 清理碎片。

### 3.3 新增表结构（遵循阿里规约）

```sql
CREATE TABLE IF NOT EXISTS file_upload_task (
    id             BIGINT AUTO_INCREMENT PRIMARY KEY,
    upload_id      VARCHAR(64)  NOT NULL COMMENT '上传任务唯一标识(UUID)',
    file_hash      VARCHAR(64)  NOT NULL COMMENT '整文件SHA-256',
    file_name      VARCHAR(500) NOT NULL COMMENT '原始文件名',
    file_size      BIGINT       NOT NULL COMMENT '文件字节大小',
    chunk_size     INT          NOT NULL COMMENT '分片字节大小',
    chunk_total    INT          NOT NULL COMMENT '分片总数',
    chunk_uploaded INT          DEFAULT 0 COMMENT '已上传分片数',
    chunk_bitmap   VARCHAR(2048) COMMENT '分片位图(Base64)，避免每次扫目录',
    user_id        BIGINT       NOT NULL COMMENT '上传者（逻辑外键 sys_user.id）',
    category_id    BIGINT       COMMENT '目标知识库（逻辑外键 doc_category.id）',
    rel_path       VARCHAR(500) COMMENT '目录导入的相对路径',
    storage_path   VARCHAR(500) COMMENT '合并后最终访问路径',
    status         TINYINT      DEFAULT 0 COMMENT '0上传中 1已合并 2已入库 3失败 4已取消',
    expire_time    TIMESTAMP    COMMENT '过期时间，超时由定时任务清理',
    create_time    TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
    update_time    TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
    deleted        INT          DEFAULT 0
);
CREATE UNIQUE INDEX uk_fut_upload_id  ON file_upload_task(upload_id);
CREATE INDEX idx_fut_hash_user        ON file_upload_task(file_hash, user_id);
CREATE INDEX idx_fut_status_expire    ON file_upload_task(status, expire_time);

-- 秒传所需：文档表补「文件字节哈希」列（现有 content_hash 是正文哈希，语义不同）
ALTER TABLE doc_document ADD COLUMN file_hash VARCHAR(64) COMMENT '原始文件字节SHA-256，用于秒传/去重';
CREATE INDEX idx_doc_file_hash ON doc_document(file_hash);
```

> ⚠️ **本项目踩过的坑**：唯一索引里**不要**混入 `deleted` 列（参见 `uk_app_user_goal` 事故）。任务记录清理一律走**物理删除**，否则重复上传同一文件会撞唯一键报 500。

### 3.4 关键参数

| 参数 | 取值 | 依据 |
|---|---|---|
| 分片阈值 | 10MB | 小文件分片得不偿失，直接走现有 `/docs/upload` |
| 分片大小 | 5MB（自适应：>1GB 用 20MB） | 控制分片总数 < 10000，避免元数据爆炸 |
| 并发数 | 3 | 浏览器同域 6 连接上限，留 3 条给其他请求 |
| 重试 | 3 次，指数退避 1s/2s/4s | — |
| 碎片过期 | 24h | 定时任务扫 `status=0 AND expire_time < now()` 清目录 |
| `max-file-size` | 调至 **10MB** | 分片后单请求变小，反而可以收紧，提升安全性 |

### 3.5 哈希计算（前端）

不能 `FileReader.readAsArrayBuffer(整个文件)` —— 2GB 文件直接爆内存。两个方案：

- **精确哈希**：`hash-wasm` 的增量 SHA-256，边切片边喂，放进 **Web Worker** 避免卡 UI。2GB 约 8～15 秒。
- **抽样哈希**（推荐默认）：`SHA256(首2MB + 中间2MB + 尾2MB + fileSize)` 作为秒传探测键，命中后服务端再做一次全量校验。2GB 耗时 < 300ms。

界面上把哈希阶段单独做成「校验中」状态，不要混进上传进度里。

## 4. 前端进度条设计

### 4.1 三级进度模型

```
批次进度 = Σ(各文件已传字节) / Σ(各文件总字节)
文件进度 = (已完成分片数 × chunkSize + Σ在途分片的 loaded) / fileSize
分片进度 = axios onUploadProgress 的 e.loaded
```

关键：用 `Map<chunkIndex, loadedBytes>` 记录在途分片，每次回调更新后重算文件进度。**不能简单用「完成分片数 / 总分片数」**——3 并发时进度条会一卡一跳。

### 4.2 状态机（UI 必须区分）

```
排队中 → 校验中(hash) → 上传中(x%) → 合并中 → 解析中 → 完成
                              ↓            ↓
                          已暂停 ←→      失败(可重试)
```

现状把「上传」和「后端解析」混在一个动画里，是用户觉得卡死的根因。解析阶段单独展示，配合异步化后的轮询/SSE。

### 4.3 展示信息

单文件行：`文件名 | 进度条 | 42% | 218MB/512MB | 3.2MB/s | 剩余 1分32秒`
速率用**滑动窗口 EMA**（近 5 秒），瞬时值抖动太大不可读。

### 4.4 暂停 / 续传

- 暂停：`AbortController.abort()` 取消在途分片请求，已完成分片保留在服务端
- 恢复：重新 `init` → 拿 `uploadedChunks` → 只传缺失的
- **刷新页面后**：用 IndexedDB 存 `{fileHash, uploadId, relPath}`，但浏览器安全策略下 `File` 对象**无法持久化**，用户必须重新选择同一文件/目录；重选后按 hash 自动匹配并跳过已传分片。这个限制要在 UI 上讲清楚，不要假装能全自动恢复。

### 4.5 Composable 骨架

```ts
// frontend/src/composables/useChunkUpload.ts
export function useChunkUpload(opts: { concurrency?: number; chunkSize?: number } = {}) {
  const tasks = ref<UploadTask[]>([])
  const overallPercent = computed(() => { /* 按字节加权，不是按文件数 */ })

  async function addFiles(files: File[], categoryId: number) { /* 入队 */ }
  async function start() { /* 文件级队列 + 分片级并发池 */ }
  function pause(taskId: string) { /* abort 在途请求 */ }
  function resume(taskId: string) { /* 重新 init → 补传 */ }
  function retry(taskId: string) { /* 仅重试失败文件 */ }

  return { tasks, overallPercent, addFiles, start, pause, resume, retry }
}
```

`UploadDoc.vue` / `KnowledgeUpload.vue` / `KnowledgeImport.vue` 三处重复实现应统一收敛到这个 composable。

### 4.6 后端解析异步化

`merge` 立即返回 `docId` + `parseStatus=PARSING`，Tika 解析与 RAG 分块投递到线程池（**按阿里规约用 `ThreadPoolExecutor` 显式构造，禁用 `Executors`**）。这样：
- 300s 超时问题消失
- Tomcat 请求线程不被长期占用
- 前端可以显示「已上传，正在解析 3/128 篇」

## 5. 存储方案对比与选型

### 5.1 逐维度对比

| 维度 | 方案一：文件落盘 + DB 存路径 | 方案二：BLOB 存数据库 |
|---|---|---|
| **写性能** | 顺序写盘，可零拷贝合并。写放大 ≈ 1× | InnoDB 双写：redo log + binlog + 数据页，写放大 **≈ 3×**。50MB 文件实际落盘 150MB+ |
| **读性能** | Nginx `sendfile` 静态直出，不占应用线程、不占 DB 连接 | 每次读经 JDBC → 应用堆 → 网络。**100MB 文件读取直接威胁 JVM 堆** |
| **Range / 断点下载** | 原生支持，浏览器可缓存、可挂 CDN | 需应用层手写字节区间，无法 CDN 缓存 |
| **缓冲池污染** | 无影响 | ⚠️ **最隐蔽的杀手**：大字段挤占 `innodb_buffer_pool`，把热点索引页刷出内存，导致**全库查询集体变慢** |
| **备份恢复** | DB 只有元数据（几十 MB），秒级备份；文件用 rsync / 对象存储版本控制做增量 | `mysqldump` 从分钟级变**小时级**；PITR 恢复时间常常不可接受 |
| **主从复制** | binlog 极小，延迟稳定 | ROW 模式下一个 50MB 文件产生 50MB+ binlog，**从库延迟飙升**，主从切换风险高 |
| **事务一致性** | ❌ 需补偿：可能出现「DB 有记录、文件丢失」或孤儿文件 | ✅ **唯一优势**：与业务数据同事务，天然原子 |
| **扩展性** | 抽象 `StorageService` 后可无缝迁 MinIO / OSS / COS，`file_url` 语义不变 | 撞到单实例存储上限后**无解**，分库分表时大字段迁移极痛苦 |
| **多实例部署** | 需共享存储（NFS / 对象存储） | 天然共享（这点方案二占优） |
| **维护成本** | 多一份文件生命周期管理：孤儿清理、目录分片、权限、防盗链 | 日常运维简单（一份备份搞定），但**超规模后迁移成本极高** |
| **安全** | 需防路径穿越、防直链、禁止可执行/HTML 直出 | 无静态目录暴露面 |

### 5.2 方案一的短板怎么补

方案二唯一真正的优势是**事务一致性**。用工程手段补齐即可，本方案的设计已经包含：

1. **先文件后事务**：合并 + 哈希校验通过 → 再开事务写 `doc_document`。事务失败则文件成孤儿（不影响正确性，只浪费空间）
2. **状态机兜底**：`file_upload_task.status` 记录每一步，异常可重放
3. **定时对账**：每日扫描 `{uploadDir}` 下无 DB 引用的文件 → 移入 `.trash/` 保留 7 天再删（**不直接 `rm`**）
4. **引用计数**：`file_hash` 相同的文件只存一份，`doc_document` 多条记录共享同一 `file_url`，删除时检查引用数

### 5.3 规模分界线

| 总存储量 | 单文件典型大小 | 推荐方案 |
|---|---|---|
| **< 1GB** | < 1MB | 方案二**可以接受**（运维最省事），或方案一 |
| **1GB ～ 100GB** | 1MB ～ 500MB | ✅ **方案一：本地磁盘 + DB 存路径** ← KnowFlow 当前位置 |
| **100GB ～ 10TB** | 任意 | 方案一进阶：**MinIO 自建对象存储**，DB 存 objectKey |
| **> 10TB / 多地域 / 需 CDN** | 任意 | 云对象存储（OSS / COS）+ **前端预签名 URL 直传**，服务端不过流量 |

**特例补充**：
- 单个 < 64KB 的小文件（头像、图标、缩略图）入库反而更划算——省一次磁盘 IO，且不产生海量小文件拖垮 inode
- 强合规场景（电子签章、审计留痕、法律证据）可以为**一致性牺牲性能**选方案二
- 文档**正文文本**继续存 `content TEXT`（现状合理），只有**原始二进制文件**走文件系统

### 5.4 对 KnowFlow 的最终建议

**维持方案一，理由三条：**

1. 当前架构已经是方案一（`doc_document.file_url` + `{uploadDir}/yyyy/MM/dd/{uuid}`），无迁移成本
2. **现实决定性因素**：项目用的是 **H2 内存数据库**（`application.yml:10-15`，`DB_CLOSE_DELAY=-1`）。BLOB 入库 = 文件全部驻留 JVM 堆，几个 PDF 就 **OOM**，方案二在当前技术栈下直接不可行
3. 知识库场景天然是「一次写入、多次读取」的大文件，正是文件系统 + CDN 的最佳适用面

**要补的三件事：**

```java
// 1) 抽象存储层，为未来迁 MinIO 留口子
public interface StorageService {
    StorageResult save(InputStream in, String originalName, long size);
    void delete(String storagePath);
    Resource load(String storagePath);
}
// 实现：LocalFileStorage（当前）/ MinioStorage（>100GB 时切换，改一行配置）
```

2. `file_hash` 去重 + 引用计数（同一份 PDF 十个人上传只存一份）
3. 孤儿文件对账定时任务（回收站语义，不直接删）

## 7. 风险与已知坑（本项目实测）

| 风险 | 应对 |
|---|---|
| 唯一索引含 `deleted` 列 → 重复上传撞唯一键报 500 | `uk_fut_upload_id` 只用 `upload_id`；清理走**物理删除** |
| Tomcat `MultipartFile.transferTo()` 相对路径 bug | 继续沿用 `UploadHelper` 的 `Files.copy(InputStream, path)` |
| H2 内存库重启数据清零，`chunks/` 目录残留 | 应用启动时清理孤儿分片目录 |
| 新接口被 `SecurityConfig` 拦截 401 | 本项目只放行白名单 GET，写接口需登录——需显式配置 |
| 多实例部署时分片散落在不同机器 | 分片目录必须落共享存储，或网关做 `uploadId` 一致性哈希 |
| 上传 `.html/.svg` 经 `/uploads/**` 直出造成存储型 XSS | 扩展名白名单 + 响应头 `Content-Disposition: attachment` + `X-Content-Type-Options: nosniff` |
| 前后端端口错位（会话注入随机 `SERVER__PORT`） | 后端强制 `--server.port=8080`，前端 `SERVER__PORT=8080` |
