# 知识库导入 · 超长 Markdown 正文（超出 maxContentChars）存储方案

> 适用前提：个人本地单机部署 + MySQL 存储（见《个人本地部署存储选型建议》）。
> 本文在用户提出的四种方案基础上，结合实际代码现状给出落地建议。

---

## 一、现状（实测，决定方案是否成立）

| 项 | 现状 | 证据 |
|---|---|---|
| 截断阈值 | 导入时默认 `maxContentChars = 50000` 字符 | `KnowledgeImportController.java:69/107` 默认 50000；`KnowledgeImportOptionsDTO.java:48` |
| 截断逻辑 | `if (content.length() > maxChars) content = substring(0, maxChars) + "\n\n...(正文已截断)"` | `KnowledgeImportServiceImpl.java:339-341` |
| **超出部分去向** | **直接丢弃，无任何保留** | 同上，仅 `substring` 不落库 |
| `content` 字段类型 | `TEXT` | `schema.sql:28` |
| 列表预览 | 列表接口已把 `content` 截断到 4000 字符做预览 | `DocServiceImpl.java:461/486`（与导入截断是两处独立逻辑） |
| AI/抽取侧截断 | 送给 LLM 的上下文另有 20000（`AiServiceImpl.java:137`）/ 实体抽取 6000（`KnowledgeService.java:771`）上限 | 与导入截断解耦，应保留 |

**最关键事实（迁移雷区）**：当前项目跑在 H2（`MODE=MySQL`），H2 的 `TEXT`/`CLOB` 实际不受 64KB 限制，所以现在一切正常。但一旦切到**真 MySQL**，`TEXT` 类型硬上限是 **65,535 字节**（UTF-8MB4 下约 16,383~21,845 字符）。这意味着：
- 连"截断到 5 万字符"的结果都**塞不进 `TEXT`**——MySQL 会按字节静默截断（SQL 模式非严格时）或直接报错（严格模式）；
- 因此 **`content TEXT` → `LONGTEXT` 不是方案四的"可选优化"，而是切 MySQL 的强制前提**。不做这步，所有超长文档在 MySQL 上都会丢尾。

另：`:363` 的 `contentHash` 是在截断**之后**计算的，导致"60k 文档"和"它的 5 万前缀"会被增量去重判为相同。改方案时需改为对**全文**哈希。

## 二、四种方案评估

### 方案一：分段存储（主表 + 子表）
- 主表 `doc_document.content` 存前 `maxContentChars`；新增 `has_more TINYINT`；子表 `doc_document_segment(doc_id, seq, content, char_count)`。
- **优点**：主表结构基本不变；预览快（列表只取前段）；全文仍在 DB 内，详情/检索都能还原；`has_more` 让前端按需再拉后续段。
- **缺点**：新增子表 + 写入/读取/拼接三段逻辑；需事务保证主表与分段一致（要么全写要么全回滚）。
- **适用**：希望全部内容留在库内、又要列表轻量。

### 方案二：摘要 + 原文外链
- `content` 存截断预览 + 末尾提示；新增 `full_content_path` 指向磁盘/对象存储上的完整 `.md`；前端"查看完整文档"按钮。
- **优点**：主表字段最干净；不碰 DB 大字段；与"文件落本地磁盘"的存储决策天然一致（原文本来就该在磁盘上）。
- **缺点**：DB 内不可直接搜超出部分（除非搜索引擎）；依赖文件路径可用性（删文件即失效）。
- **适用**：超长文档仅存档、偶尔看全文；且已按存储方案把原文落盘。

### 方案三：全文索引外置（ES / Meilisearch）
- `content` 存截断预览；完整文本进搜索引擎，关联 `doc_id`；列表走 DB、搜索/详情走引擎。
- **优点**：搜索能力跃升，彻底摆脱字段长度与 DB 查询压力。
- **缺点**：引入额外组件、数据同步链路、运维成本。**对个人本地严重过度设计。**
- **适用**：多人/生产、强搜索需求。**不推荐本场景。**

### 方案四：字段类型扩容（TEXT → LONGTEXT）
- `content` 改为 `LONGTEXT`（MySQL 上限 4GB），移除应用层 50000 截断，仅做文件大小校验（如 ≤10MB）。
- **优点**：**零新增表、零分段逻辑、一劳永逸、不丢任何数据**；列表接口本就只回 4000 字预览，不受影响。
- **缺点**：单字段可达数 MB；若未来做"列表批量带回 content"会涨 payload——但本项目列表已截断，无此问题；需配 `max_allowed_packet` > 最大文档。
- **适用**：**个人本地 MySQL 的最轻量解**。

## 三、推荐组合（针对个人本地 + MySQL）

### 必做前提（不可省略）
1. `doc_document.content` 由 `TEXT` 改为 **`LONGTEXT`**（否则 MySQL 静默截断）。
2. 校验 `max_allowed_packet`（MySQL 默认 64MB）> 你允许的最大单文档（建议设 `max_allowed_packet=64M`，对应 ≤ ~16MB 的 Markdown）。

### 路线 A（最轻量，推荐首选）：纯方案四
- 改 `LONGTEXT` + **去掉导入侧的 50000 截断**（保留 AI 侧 20000/6000 截断不变）。
- 新增 `content_hash` 改为对**全文**计算，保证增量去重正确。
- **零新表、零分段逻辑、不丢数据**，对个人单机完全够快。
- 代价：单文档上限由"字符数"变为"文件大小"（如 ≤10MB）。

### 路线 B（要列表轻量 + 全文在库）：方案一 + 方案四
- `LONGTEXT` 前提下，仍按 `maxContentChars` 在**应用层**把正文拆成"主表前段 + `doc_document_segment` 后续段"，`has_more` 标记。
- 好处：详情页/检索能还原完整正文，列表只取前段，DB 行不变胖。
- 适合你"既想预览快、又不想丢超长内容"的偏好。

### 为什么本场景不推方案三
个人本地跑 ES/Meilisearch 是杀鸡用牛刀；方案二/四已覆盖"存档"与"不失真"需求。

### 决策表

| 你的诉求 | 推荐 |
|---|---|
| 个人用、要最简单、不丢数据 | **路线 A：方案四（LONGTEXT + 去截断）** |
| 列表要轻 + 全文留库内 | **路线 B：方案一 + 方案四** |
| 超长仅存档、已落盘原文 | 方案二（外链，复用存储层） |
| 强搜索/多人 | 方案三（不在本场景） |

## 四、落地代码片段（路线 B 示例）

### DDL（schema.sql 追加/修改）
```sql
-- 主表字段调整
ALTER TABLE doc_document MODIFY COLUMN content LONGTEXT;
ALTER TABLE doc_document ADD COLUMN has_more TINYINT NOT NULL DEFAULT 0 COMMENT '正文是否超出 maxContentChars';

-- 分段子表
CREATE TABLE IF NOT EXISTS doc_document_segment (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    doc_id      BIGINT NOT NULL COMMENT '逻辑外键 doc_document.id',
    seq         INT  NOT NULL COMMENT '分段序号，从 1 开始',
    content     LONGTEXT NOT NULL COMMENT '第 seq 段正文',
    char_count  INT  DEFAULT 0,
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
    update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    deleted     INT DEFAULT 0,
    UNIQUE KEY uk_seg_doc_seq (doc_id, seq, deleted)
) COMMENT='超长文档正文分段';
CREATE INDEX idx_seg_doc ON doc_document_segment (doc_id);
```
> 唯一索引 `uk_seg_doc_seq` 含 `deleted` 列——但与 `file_upload_task` 不同，segment 是可重写的（重新导入覆盖分段），建议**物理删除旧分段后重写**，避免重复 `doc_id+seq` 撞键（复用 `uk_app_user_goal` 那次 500 的教训）。

### 写入改造点（KnowledgeImportServiceImpl.java:339-341）
```java
// 原：content = content.substring(0, maxChars) + "...(正文已截断)"; // 丢弃超出部分
// 改：
String full = content;
if (full.length() > maxChars) {
    String head = full.substring(0, maxChars);
    doc.setContent(head);
    doc.setHasMore(1);
    // 落 segment：按 maxChars 切片，seq 从 1 起
    List<DocDocumentSegment> segs = sliceSegments(full, maxChars);
    segmentMapper.insertBatch(segs);   // 与 doc 同事务
} else {
    doc.setContent(full);
    doc.setHasMore(0);
}
// contentHash 改对 full 计算（修复增量去重误判）
doc.setContentHash(DigestUtil.sha256(full));
```

### 读取还原（详情接口）
```java
if (doc.getHasMore() == 1) {
    List<DocDocumentSegment> segs = segmentMapper.listByDocId(docId); // ORDER BY seq
    StringBuilder sb = new StringBuilder(doc.getContent());
    segs.forEach(s -> sb.append(s.getContent()));
    return sb.toString();
}
return doc.getContent();
```

## 五、结论
- **切 MySQL 前先把 `content` 改成 `LONGTEXT`**，否则超长文档会被静默截断——这是所有方案的共同前提，优先级高于选型本身。
- 个人本地场景：**路线 A（纯方案四）最省事**；若你偏好"列表轻 + 全文在库"，用**路线 B（方案一 + 方案四）**。
- 不要为个人本地引入 ES（方案三）；方案二仅在"已落盘原文"时作为轻量外链备选。
- 记得把 `contentHash` 改为对**全文**哈希，否则增量导入去重会误判。
